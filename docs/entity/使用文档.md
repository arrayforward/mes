# 实体搜索树子系统 使用文档

> 本文面向**上层模块的调用方**：意图/行为系统、LLM 适配器、叙事引擎、
> 感知层网关的开发者。设计原理见 [设计文档.md](设计文档.md)。

## 1. CMake 集成

entity 组件以 `add_subdirectory` 引入，自动连带引入兄弟工程 storage
（unistore）与 geocore——三者为同机源码树，路径可用 cache 变量覆盖：

```cmake
# 上层 CMakeLists.txt
add_subdirectory(D:/manufacture/entity ${CMAKE_BINARY_DIR}/entity)
target_link_libraries(your_target PRIVATE entity_algo)

# 源码树不在默认位置时：
#   cmake -DENTITY_STORAGE_DIR=/path/to/storage -DENTITY_GEOCORE_DIR=/path/to/geocore
```

所需头文件：

```cpp
#include "entity/resolver.h"                  // entity::Resolver / ResolverConfig / SearchHit
#include "entitytree/backends/sql_store.h"    // entitytree::SqlEntityStore（换后端只换头文件与类名）
```

## 2. Resolver API 参考

`entity::Resolver` 是全部算法入口，构造时注入存储与配置：

```cpp
using namespace entity;
using namespace entitytree;

SqlEntityStore store("world.db");
ResolverConfig cfg;
cfg.bucket_size = 300;
cfg.theta_form = 3.0;
cfg.attribute_weight = {{"plate_number", 3.0}, {"color", 1.0}, {"brand", 1.0}};
Resolver resolver(store, cfg);
```

### 2.1 ingest —— 摄入观测

```cpp
std::string ingest(const entitytree::Observation& obs);   // 返回所属侧写 profile_id
```

按 `(anchor_ref, timestamp / bucket_size)` 找到或创建 level 0 细桶侧写
（多级配置下用 `bucket_sizes[0]` 作桶长），追加属性条目、重算 info_score；
达 `theta_form` 且侧写仍在 pool → 置 emerged 并自动 resolve
（合并 / 新建 / 存疑）。`observation_id` 留空由系统自动生成（"ob-..."）。

```cpp
auto p1 = resolver.ingest(obs("plate_number", "沪A12345", 0.95, "cam1", "gate-1", 100));
resolver.ingest(obs("color", "red", 0.9, "cam1", "gate-1", 110));
resolver.ingest(obs("brand", "VW", 0.85, "cam1", "gate-1", 120));
// 第三条后 info_score≈3.47 ≥ 3.0 → 浮现，无候选实体 → 自动新建实体
std::string e1 = store.effective_binding(p1)->entity_id;
```

### 2.2 resolve —— 手动触发解析

```cpp
void resolve(const std::string& profile_id);
```

对侧写做 blocking 召回 → 打分 → 三区间决策。ingest 达阈值时会自动调用；
上层一般只在**人工干预后**（如手动改了侧写状态、补了观测想重新判定）
显式调用。

### 2.3 split —— 拆分（误合并纠正）

```cpp
std::string split(const std::string& profile_id,
                  const std::string& new_entity_name = "");   // 返回新实体 entity_id
```

把指定侧写从当前实体解绑：新建实体并追加 kind="split" 的绑定指向它
（latest wins，历史全保留），新旧实体各自重建 merged view 与 credibility。
被拆侧写的来源 reliability 下调 `source_penalty`。侧写未绑定抛
`entitytree::EntityTreeError`。

```cpp
// 人工复核：第二个侧写其实是另一辆同款车
std::string e2 = resolver.split(p2, "嫌疑车B");
for (const auto& b : store.bindings_of(p2))   // merge + split 两条历史都在
    printf("[seq=%lld] %s → %s\n", (long long)b.seq, b.kind.c_str(),
           b.entity_id.c_str());
```

### 2.4 search —— 实体检索

```cpp
std::vector<SearchHit> search(
    const std::vector<std::pair<std::string, std::string>>& query_attrs,
    size_t topk, double min_credibility = 0.0, int64_t now = 0);
```

多路属性召回取并集，`final = alpha × match_score + beta × 有效可信度`
降序取 topk；有效可信度 < min_credibility 的实体被过滤。
`now = 0`（默认）不启用时效语义；`now > 0` 时排序用半衰期衰减后的有效
可信度，命中属性乘新鲜度因子（需配置对应 half_life，否则因子恒 1）。

```cpp
for (const auto& h : resolver.search({{"plate_number", "沪A12345"}}, 10)) {
    // h.entity_id / h.match_score / h.credibility / h.final_score / h.explanation
}
// 带时效与可信度门槛的决策式检索：
auto hits = resolver.search({{"color", "red"}}, /*topk=*/5,
                            /*min_credibility=*/0.4, /*now=*/current_ts);
```

`SearchHit` 字段：`entity_id`、`match_score`（0~1，含新鲜度折算）、
`credibility`（有效值；未配半衰期 = 基准值）、`final_score`、`explanation`
（json 数组，逐属性明细，见 §3.4）。

### 2.5 effective_credibility —— 查询时有效可信度

```cpp
double effective_credibility(const std::string& entity_id, int64_t now);
```

`base × 0.5^((now − updated_at)/credibility_half_life)`；未配半衰期或
`now ≤ updated_at` 时原样返回基准值。存储的基准值永不改写。

### 2.6 rebuild_entity —— 重建实体视图

```cpp
void rebuild_entity(const std::string& entity_id);
```

从全部有效侧写重建 merged view 并重算 credibility 基准值与 updated_at，
view_version +1。resolve/split 内部自动调用；上层在**直接改了存储层数据**
（如手工批量导入侧写）后用它刷新缓存。merged view 只聚合 level 0 细桶
侧写（rollup 粗桶侧写是派生镜像，不重复计分）。

### 2.7 rollup —— 多分辨率时间桶上卷

```cpp
std::vector<std::string> rollup(const std::string& entity_id, int level);
                                // 返回新建的粗桶侧写 id 列表
```

把该实体在 level-1 层的全部已链接细桶侧写按 level 层粗桶分组聚合出粗桶
侧写（属性并集、status=linked、追加 note="rollup L{level}" 的 merge 绑定），
细桶镜像原样保留。幂等：同粗桶已有粗侧写则跳过；单级配置返回空。
**调用时机建议**：由上层维护任务周期触发（如每小时对活跃实体跑一次
`rollup(eid, 1)`、每天一次 `rollup(eid, 2)`），不要在 ingest 热路径上调；
观测稀疏时段（夜间）跑收益最大——粗桶侧写让常驻实体在细桶无候选时仍可
被 blocking 召回。

### 2.8 set_distance_provider —— 轨迹连续性校验

```cpp
using DistanceProvider =
    std::function<std::optional<double>(const std::string& anchor_a,
                                        const std::string& anchor_b)>;
void set_distance_provider(DistanceProvider provider);
```

注入两锚点直线距离（米）的提供者；返回 nullopt = 无数据不约束。配合
`max_speed > 0` 启用：合并打分前检查"距离 ≤ max_speed × Δt"，违反时按
`trajectory_check` 处置（veto 排除 / penalty 压分）。geocore 适配器：

```cpp
#include "entity/geocore_distance.h"
geocore::Kernel kernel;
/* CreateScene / CreateAnchor ...; kernel.BeginFrame(t); */
resolver.set_distance_provider(entity::make_geocore_distance(kernel, /*frame_time=*/0.0));
// anchor_ref 用 geocore 路径码（"1/256/..."）时，距离由内核 Convert 精确给出
```

## 3. 上层调用场景流程

### 3.1 感知层 / 事件系统 → ingest 观测

Observation 字段填写约定：

| 字段 | 约定 |
|---|---|
| `observation_id` | 留空（系统生成 "ob-..."）；自带 id 可保证重放幂等（重复 id 被存储层拒绝） |
| `attribute_key` | 蛇形命名，全系统统一词表：`plate_number` / `face_desc` / `color` / `brand` / `model`……新 key 加入前先评审进词表 |
| `value` | 文本化的值（向量/embedding 检索是规划中的扩展，本期不做） |
| `confidence` | 感知器对自身**这一次观测**的置信度 0~1；不要预先乘来源可靠性（那是 et_sources 的职责，系统会自动折算） |
| `source_id` | 来源稳定标识（摄像头编号 / LLM 模型版本 / 工号）；info_score 数的就是它，**同一物理来源必须始终用同一个 id** |
| `anchor_ref` | 空间锚点；推荐 geocore 路径码（如 `"1/1/2/3"`），层级邻近召回生效；自由字符串（如 `"gate-1"`）退化为等值语义 |
| `timestamp` | 物理时间（秒），决定时间桶归属与衰减基准 |
| `event_ref` | 可空；填 eventstore 中的溯源事件 id，打通"证据来自哪段叙事" |

### 3.2 行为 / 决策系统 → search 检索

- **调查场景**（"找出所有像这辆车的实体"）：放宽召回、重匹配——
  `alpha` 调高（如 0.8/0.2）、`min_credibility = 0`、topk 放大；
- **决策场景**（"我要对它下注，只接受可靠结论"）：重可信度——
  `beta` 调高（如 0.5/0.5）、设 `min_credibility`、传 `now` 启用衰减，
  陈旧结论自动降权；
- disputed 状态的实体仍在检索结果中（status 不过滤），需要排除时
  取回 `get_entity(h.entity_id).status` 自行过滤。

### 3.3 人工 / LLM 干预 → 纠正系统误判

正确姿势（全部 append-only，不删不改历史）：

- **误合并** → `resolver.split(profile_id, "名称")`；
- **漏合并**（两个实体其实是同一个）→ 直接追加绑定：
  把实体 B 的全部有效侧写逐一对实体 A `append_binding`
  （`EntityBinding{new_id("bd"), profile_id, entityA, conf, "manual", note}`），
  然后 `resolver.rebuild_entity(entityA)` 与 `rebuild_entity(entityB)`；
- **状态流转**：candidate → confirmed 由人工确认后 `get_entity` + 改
  status + `upsert_entity`；disputed 实体补证据后等下一次 resolve 或
  人工走"漏合并"路径。

### 3.4 结果可解释性 → explanation 与溯源

```json
// SearchHit.explanation 的一个条目
{"key": "plate_number", "value": "沪A12345", "weight": 3.0,
 "hit": true, "freshness": 1.0, "latest_ts": 370}
```

读法：该实体因属性 `plate_number=沪A12345` 命中，区分度权重 3.0，
freshness 为该属性的时效因子（未配半衰期恒 1.0），latest_ts 为该属性
最新观测时间。继续溯源：

```cpp
for (const auto& p : store.profiles_of_entity(h.entity_id))   // 实体的全部有效侧写
    for (const auto& en : p.attributes["plate_number"])
        auto o = store.get_observation(
            store.query_observations("plate_number", {}, p.anchor_ref)[0].observation_id);
// 侧写 attributes 条目里的 obs_seq / source_id / ts 直接对应 et_observations 原始记录
```

## 4. EntityStore 查询原语速查

上层大多数时候只用 Resolver；以下情况直接用存储接口：

| 需求 | 接口 |
|---|---|
| 取观测原文 / 按来源对账 | `get_observation(id)` / `query_observations(key?, source?, anchor?)` / `observations_of(anchor)` |
| 看侧写镜像与状态 | `get_profile(id)` / `query_profiles(anchor?, bucket_from?, bucket_to?, status?, level?)` |
| 属性召回（绕过打分） | `find_profiles_by_attribute(k,v)` / `find_entities_by_attribute(k,v)` |
| 看实体当前态 | `get_entity(id)`（credibility 为基准值，updated_at 为基准时间） |
| 审计绑定历史 / 有效归属 | `bindings_of(pid)` / `effective_binding(pid)` / `profiles_of_entity(eid)` |
| 干预：手动绑定 / 改状态 | `append_binding(b)`（append-only）/ `upsert_entity(e)` |
| 来源画像读写 | `upsert_source(s)` / `get_source(id) → optional` / `list_sources()` |

错误语义：`get_*` 不存在抛 `entitytree::NotFoundError`；重复 observation_id
抛 `DuplicateError`；`append_binding` 引用的侧写/实体不存在抛 NotFoundError。

## 5. ResolverConfig 全参数表

| 参数 | 类型 | 默认值 | 含义 | 调参建议 |
|---|---|---|---|---|
| `bucket_size` | int64_t | 300 | 时间桶粒度（秒） | 按巡检节拍设；0 表示全部同桶（不建议） |
| `theta_form` | double | 3.0 | 浮现阈值（信息量） | 单源密集场景降到 2.0 |
| `theta_merge` | double | 0.75 | 合并阈值 | 强标识主导可 0.7；误合并多就调高 |
| `theta_split` | double | 0.30 | 新建阈值（与 θ_merge 之间为存疑区） | 实体库膨胀就调高 |
| `min_lca_depth` | int | 0 | 锚点 LCA 邻近阈值（0=只要求同根） | 生产建议 ≥1 |
| `attribute_weight` | map<string,double> | {}（缺省 1.0） | 属性区分度权重 | 车牌/序列号 3.0，描述性 1.0 |
| `alpha` | double | 0.7 | 检索排序：匹配度权重 | 调查 0.8，决策 0.5 |
| `beta` | double | 0.3 | 检索排序：可信度权重 | 与 alpha 配对调整 |
| `credibility_half_life` | double | 0 | 实体可信度半衰期（秒），0=不衰减 | 日级变化场景 86400 起试 |
| `attribute_half_life` | map<string,double> | {}（缺省 0=不衰减） | 按 key 的属性半衰期（秒） | 只给易变属性设 |
| `source_reward` | double | 0.02 | merge 成功来源可靠性上调（封顶 1.0） | 保持小于 penalty |
| `source_penalty` | double | 0.05 | split 发生来源可靠性下调（封底 0.05） | 错罚 > 对奖 |
| `bucket_sizes` | vector<int64_t> | {}（空=单级，用 bucket_size） | 时间桶分辨率梯子（秒，level 0 最细） | {300, 3600, 86400} |
| `max_speed` | double | 0 | 轨迹校验最大速度（m/s），0=关闭 | 车辆 20~40，人 2 |
| `trajectory_check` | string | "veto" | 违反时 "veto" 排除候选 / "penalty" 压分 | 强物理场景 veto |
| `trajectory_penalty` | double | 0.5 | penalty 模式压分因子 | 0.5 |

## 6. 部署

### 6.1 后端选择

起步用 **sqlite 单机**（`SqlEntityStore("world.db")`），零运维、可直接用
sqlite 工具查验 et_* 七张表；服务化再切 mysql/postgres；memory 仅测试用；
file 可人读调试；redis 适合中小数据量的缓存层。
换后端只换头文件与类名（`MemoryEntityStore / SqlEntityStore /
FileEntityStore / RedisEntityStore / MySqlEntityStore / PgEntityStore`）。

### 6.2 et_sources 共享（制造业单库部署）

entitytree 与 voxelstore **指向同一个数据库文件**（如同一个 `world.db`
或同一个 MySQL 库），et_sources 即被 stmb 观测管线仲裁与 entity 组件
天然共用。双向同步**已实现**（v6 起）：

- **stmb 侧落盘**：SourceRegistry 随快照/manifest 的 SnapSource 小节与
  RegisterSource WAL 记录持久化（formatVersion 6），重启不再丢权重；
- **双向桥**：voxel 以 `-DSTMB_WITH_UNISTORE=ON` 构建
  （`-DUNISTORE_DIR=` 指向 storage 源码目录，默认已是），用
  `stmb::UnistoreSourceBridge`（`src/bridge/`）连接 stmb 服务与指向
  同库文件的 `entitytree::SqlEntityStore`——构造即把 et_sources 水合进
  stmb 注册表（**以表为准**，entity 反馈闭环是最新证据），并安装变更
  钩子把 stmb 的 registerSource 写回 et_sources。voxel 默认构建仍保持
  零第三方依赖，桥只在显式开启时编译。

部署步骤：

1. stmb 与 entity 组件指向同一个 sqlite 库文件（如 `world.db`）；
2. 来源 id 统一用**数值**（桥按十进制互转 u64 ↔ 字符串；表中非数值 id
   水合时跳过，不参与 stmb 仲裁）；
3. sqlite 文件锁：两进程避免同时写——单写者原则（错开写窗口）或同进程
   内共享存储实例；高并发场景改用 mysql/pg 后端。

注意默认值差异：stmb 未知来源默认 **0.5**，entitytree 未注册默认
**1.0**——桥只同步显式注册过的 id，不动默认值；接入时注意对齐预期。

### 6.3 线程模型

单线程设计（sqlite 以 `SQLITE_THREADSAFE=0` 编译）。多线程调用方在外层
加互斥锁（与 voxel 服务层"统一互斥锁"模型一致）。

### 6.4 已知边界

- mysql / pg / redis 后端的一致性套件已实现，但真实联测需要对应服务与
  环境变量（`UNISTORE_MYSQL_DSN` / `UNISTORE_PG_CONNINFO` /
  `UNISTORE_REDIS_ADDR`）；memory / sqlite / file 每轮全量回归；
- blocking 的锚点召回是"±1 时间桶全量 + 路径邻近过滤"，桶内数据量极大时
  是扫描成本，后续可加路径前缀索引；
- 属性值为文本等值匹配；向量/embedding 召回是规划中的扩展；
- `min_lca_depth` 默认 0 意味着任意两个路径码锚点互为邻近（共享全局根），
  生产配置请显式设 ≥1；
- **level 方向与 stmb 相反**：entitytree 的 level 0 最细、stmb 的 level 0
  最粗，两个系统各自约定，混用时勿混淆；
- rollup 粗桶侧写的代表锚点取"最新观测侧写的锚点"——跨锚点合并的实体
  粗桶锚点有代表性损失（blocking 主要靠属性召回兜底）；
- 轨迹校验的距离完全依赖注入的 DistanceProvider：provider 返回 nullopt
  一律不约束（无数据 ≠ 判负），未配 provider 或 `max_speed=0` 时校验关闭；
- et_sources 的 source_id 是字符串、stmb SourceId 是 u64——桥按十进制
  互转，共享部署请统一用数值来源 id（非数值 id 水合跳过）。
