# 基于车间世界模型的业务开发说明（v1）

> **读者**：在本系统上开发业务的工程师、实施顾问、（以及 AI 协作者）
> **前置阅读**：《系统API设计_事件即接口》v3
> **一句话**：业务开发 = 四件定义工作——**编词典、立行为、立法、开窗口**。你不写业务代码，你产出定义数据。

---

## 〇、心智模型（一页纸）

- 四原语：**本体**（体，id + k-v 属性聚合，无类）、**事件**（变，本体的变化描述）、**规则**（法，属性谓词 + 纯函数）、**视图**（看，四元组契约）
- 事件原子形态：**某本体的某属性，在某时空，变成了某值**
- 两个动词：`POST /events`（提交变化描述）、`GET /views/{viewId}`（求值视图）
- 四个数据集合：属性字典、事件类型注册表、规则集、视图注册表——**未登记的键 = 编译不过**
- 三条铁律：事实终局（无 update/delete，纠错=新事件）；语义只增不改；定义未结算不生效

## 一、开发总流程

接到一个业务需求（例如"上线返修流程"），按五步展开：

```
[1] 拆事实：这个业务里会发生什么？——每个"发生"列成一句"某本体的某属性在某时空变成某值"
[2] 编词典：句子里出现的每个"属性方面"，查字典有没有；没有 → 起草定义候选
[3] 立行为：每个"发生"注册为事件类型（必填键/可选键/修正类型配平）
[4] 立法：什么条件下允许发生？派生什么？触发什么？——写成规则
[5] 开窗口：谁需要看见/操作？——定义视图四元组与角色变体
```

然后：接适配器（若涉及设备/外部系统）→ 测试（第八节）→ 定义评审（第十节）→ 结算上线。

**四维分解备忘**：一个业务事实的每个名词先归维度——本体（被观察的存在）/ 属性（方面）/ 值（状态）/ 时空（坐标）。判据：这个事实上，它是被观察的存在，还是观察的坐标？（"左前门"：缺陷定位里是空间，法规件追溯里是本体。）

## 二、第一件：编词典

**操作**：通过字典管理模块提交 `AttributeRegistered` 定义候选 → 校验 → 评审 → 结算生效。

**条目写法**：

```yaml
key: 车漆                 # 域内唯一；跨域引用用 car.车漆
semantic: 车身漆面的完好状态，终检工位目检结论
datatype: enum
range: [完好, 划痕, 凹陷, 色差]     # 值域：方面可取的状态
unit: null
writers: [DefectRegistered, InspectionDataRecorded]   # 写授权
kind: 原生                 # 派生属性须填 rule_ref
```

**纪律**：
- 键名只描述**方面**，不携带空间/部件/主体（"车漆"✓，"左前门车漆划痕"✗——方位归时空树，主体归本体）
- 语义只增不改；要改语义 → 注册新键 + 弃用旧键（`deprecated` + `replaced_by`）
- 新键先过一问：**"你是新维度，还是已有维度的新组合？"**组合进值域，不进键
- 单位必填（物理量）；禁止同名异义、异名同义

## 三、第二件：立行为

**操作**：提交 `EventTypeRegistered` 定义候选。

```yaml
type: DefectRegistered
required_keys: [id, actor, 车漆]        # 所有键须在字典登记
optional_keys: [evidence, space, remark]
rules: [R-QUAL-011]                     # 引用规则集
correction: DefectCancelled             # 修正类型必须配平——每个类型注册时想好"错了怎么办"
multi_target: false
settlement: sync                        # 操作型视图要求同步返回
```

**纪律**：
- 每个类型必须配平修正类型（冲正/作废/复核改判），没有例外
- 高频机器信号（PLC 原始流）**不是**事件类型——先过适配层三层过滤，迁移沿才有资格注册为类型
- 类型永不删除，只有弃用

## 四、第三件：立法

**规则 = 属性谓词 + 确定性纯函数**，三种效果：

| 效果 | 用途 | 例 |
|---|---|---|
| 过滤 | 合法性校验（写侧决策环 + 读侧按钮可用性，同一份） | "仅 状态∈{已下达,开工中} 的工单可报工" |
| 推导 | 派生属性 | "OEE = 可用率×性能率×良品率"（字典登记派生键时引用本规则） |
| 触发 | 产生新事件候选 | "同检点一日相同故障≥3次 → 发起 AlarmEscalated 候选" |

**写法（JS/TS 或任意语言编译 WASM，宿主契约相同）**：

```js
// 过滤规则：仅 状态∈{已下达,开工中} 的工单可报工
rule({
  id: "R-QUAL-011",
  deps: ["状态"],                  // 声明读取的字典属性——未声明的键对你不可见
  effect: "filter",
  eval(attrs, candidate) {         // attrs 由引擎按 deps 注入，只含声明的键
    return ["已下达", "开工中"].includes(attrs.状态)
      ? pass()
      : reject("R-QUAL-011：当前状态不允许报工");
  }
})

// 推导规则：派生属性
rule({
  id: "R-KPI-001",
  deps: ["可用率", "性能率", "良品率"],
  effect: "derive",
  target_key: "OEE",               // 字典中登记的派生键，rule_ref 指回本规则
  eval(attrs) { return attrs.可用率 * attrs.性能率 * attrs.良品率; }
})

// 触发规则：产生新事件候选
rule({
  id: "R-ALM-003",
  deps: ["同故障日计数", "检点"],
  effect: "trigger",
  eval(attrs) {
    if (attrs.同故障日计数 >= 3)
      return emit({ type: "AlarmEscalated", level: "科长", station: attrs.检点 });
    return noop();
  }
})
```

**硬约束**：
- **无环境**：沙盒里没有 `Date.now()`、没有 `Math.random()`、没有网络/文件/数据库——需要"当前时间"就从 candidate 的时空戳里取；任何环境能力的伸手都使审计重放失效
- **deps 之外不可见**：引擎只注入声明的键；想多读一个属性，先改 deps 声明（改动即评审点）
- deps 引用的键必须已在字典登记——编译期静态检查，未登记 = 编译不过
- 按属性存在性匹配，不按类型归属——没有类
- 规则即代码：进版本库、要评审、要单测；版本哈希被事件钉死，改规则不改历史判决
- **上线只走烘焙管线**：提交源码 → 系统编译 → 静态检查 → 沙盒试跑 → 结算生效。**禁止手工放置编译产物**；CI 可预烘（同一管线提前暴露问题），正式烘焙发生在定义结算时；编译失败 = 定义候选被拒，不是运维事故

**常见归约提醒**：状态机=作用于状态属性的过滤规则族；工作流=前置链；权限=对 actor 属性的过滤规则。**不要新建"权限模块""状态机模块"——它们都是规则。**

## 五、第四件：开窗口

**操作**：提交 `ViewRegistered` 定义候选，填四元组：

```yaml
view_id: V-REWORK-001
queries:
  events: [ReworkRequested, ReworkRecorded, ReworkSubmitted, RecheckJudged, ReworkClosed]
  fold: 终态 + 流水                  # 口径声明：L1+L2 同列可见
  spacetime: 当前车间
selects: [VIN, 缺陷部位, 故障模式, 返修内容, 复检结论]   # 字典已登记键，可跨本体
rules: [R-QUAL-020]                  # 决定行/列/按钮，与写侧同一份
emits: [ReworkRequested, ReworkRecorded, ReworkSubmitted, RecheckJudged]  # ②的子集
render_mode: 流水                    # 终态 | 流水 | 拦截
variants:
  返修工: {列: [VIN, 缺陷部位, 返修内容], emits: [ReworkRecorded, ReworkSubmitted]}
  复检员: {列: [VIN, 返修内容, 复检结论], emits: [RecheckJudged]}
```

**纪律**：
- 视图只读：视图定义里不存在任何写路径；写出口只有 emits
- 角色差异用 variants 表达，不复制新视图
- AS OF t 是所有视图的免费能力，不要在视图里自行实现时间过滤

## 六、端到端示例：返修流程上线

1. **拆事实**：发起返修 / 记录返修内容 / 递交复检 / 复检判定 / 关闭——五次发生，加修正（误判改判）
2. **编词典**：`返修内容`、`复检结论`（值域 OK/NOK）等 6 个新键候选
3. **立行为**：5 个事件类型 + 1 个修正类型（`JudgementOverruled`），修正配平
4. **立法**："仅 锁定状态=已锁 的车辆可发起返修"（过滤）；"复检 NOK → 自动发起新返修候选"（触发）
5. **开窗口**：上文 V-REWORK-001
6. **接入口**：扫 VIN 进返修（扫码适配器）
7. **测试**：第八节清单
8. **评审结算**：第十节清单 → 上线，无需停机（定义热更新）

## 七、适配器开发

适配器契约：**输入外部信号，输出变化描述，别无其他。**

- 物理动作（扫码/RFID/按钮）→ 翻译为 `{type, id, actor, ...}` 提交
- 高频信号（PLC）→ 必须前置三层过滤（迟滞+驻留+聚合网关），迁移沿才成候选
- 外部系统（ERP/WMS）→ 报文翻译；外部单号进 `evidence` 键，作为对账依据
- 适配器不得直连投影库、不得绕过 `POST /events`——绕过即破坏事实终局

## 八、测试与验证

| 测试 | 内容 | 红线 |
|---|---|---|
| 重放一致性 | 同一事件流重放 3 次，投影哈希一致 | 逐比特一致，不容差异 |
| 规则单测 | 纯函数：构造输入断言输出 | 任何副作用即违规 |
| 读写一致性 | 界面上能点的 ⇔ 系统能结算的 | 两者必须数学一致（同一份规则） |
| 修正链测试 | 每个类型走一遍"结算→修正→终态正确、原事件永存" | 原事件不可消失 |
| 噪声注入 | 适配层灌噪声，事件率有界 | 洪峰下零污染 |

## 九、纪律清单（红线）

1. 无 update/delete——纠错只能发修正事件
2. 未登记的键 = 编译不过——不允许"先用着，回头补登记"
3. 语义只增不改——改语义 = 新键弃旧键
4. 视图不存状态、不写逻辑——逻辑只在规则集
5. 事件不落模糊原文以外的"清洗值"——原文永存，解析结果另存且可修正
6. 适配器不绕端点
7. 规则跑在无环境沙盒里：纯函数，deps 声明之外的键不可见，伸手拿环境能力（时钟/随机数/网络/数据库）即违规

## 十、定义评审清单（结算前必过）

- [ ] 每个新键：是新维度还是已有维度的组合？语义定义能消歧吗？单位呢？
- [ ] 每个新事件类型：修正类型配平了吗？高频信号是否误注册（应走三层过滤）？
- [ ] 每条新规则：纯函数吗？谓词引用的键都登记了吗？
- [ ] 每个新视图：四元组完整吗？queries 的口径（L0/L1/L2）声明了吗？角色差异该用 variants 吗？
- [ ] 跨域引用的键带全名（`domain.key`）了吗？
