# 系统 API 设计：事件即接口（v3）

> **前置文档**：《MES视图研讨纪要_从页面清单到存在论分层》（四原语地基）、《西门子MES整车厂案例_视图提取》（v7，46 视图清单与事件映射）
> **设计前提**：四原语——本体（体）、事件（变）、规则（法）、视图（看）。用户的一切操作都是事件；事件 = 属性变化的描述，纯 k-v，无特权字段（type、id、actor、corrects 全是普通键）。
> **一句话**：写侧一个端点 + 一张事件类型注册表；读侧一个端点 + 一张视图注册表。没有第三种资源。
>
> **v2 修订**：按最终讨论结论全面重写——①事件原子形态定为"**某本体的某属性，在某时空，变成了某值**"，payload 最小内核 = `{id, 属性键, 新值}` + 时空戳；②业务事实的四维分解（本体/属性/值/时空）各归各的治理：注册、字典、值域、时空树；③属性字典改为**按领域分治**（方言、域内省略、跨域全名）；④新增"定义层"：字典管理模块 = 系统定义的符号表，定义与运行共用候选-结算机制。
>
> **v3 修订**：定义层落实为**四个数据集合**（属性字典 / 事件类型注册表 / 规则集 / 视图注册表），给出各自条目 schema。关键决策：定义是数据不是远程调用——定义动作对上层业务开发暴露为系统内部方法调用，运行侧启动时整体加载四集合快照，运行中由定义事件热更新；四集合本身是定义事件流的物化投影。业务开发收敛为四件定义工作：编词典、立行为、立法、开窗口。

---

## 一、总形状：两个动词

| 侧 | 动词 | 端点形态 | 语义 |
|---|---|---|---|
| 写 | **提交变化描述** | `POST /events` | 声明一次发生："谁对什么改变了哪些属性"。返回候选回执 |
| 读 | **求值视图** | `GET /views/{viewId}?observer=&entity=&t=` | 按视图契约（queries/selects/rules/emits）渲染截面 |

**没有 update、没有 delete。** 纠错 = 提交修正类型的新变化描述（携带 `corrects: 原事件id` 键）。传统 REST 的 CRUD 被消灭——U 和 D 恰恰是违反事实终局的两个动词。

**没有版本号。** 新增业务 = 注册新事件类型，不新增端点、不改旧契约。API 的演化是 append-only 的，与事件树同构。

## 二、写侧：事件的原子形态

> **事件 = 某本体的某属性，在某时空，变成了某值。**

任何业务事实进系统前做四维分解，各归各的治理：

| 维度 | 回答 | 治理者 |
|---|---|---|
| 本体 | 谁（哪个存在物） | 注册机制（首个携带 id 键的事件；无独立 create） |
| 属性 | 哪个方面 | **属性字典**（第四章） |
| 值 | 变成了什么 | 该属性条目里的值域约束 |
| 时空 | 何时何地 | **时空树子系统**（第五章） |

payload 最小内核 = `{id, 属性键, 新值}` + 时空戳，其余皆为按需附加的普通键：

```json
{
  "type": "DefectRegistered",          // 类型也是普通键——payload 自描述
  "id": "VIN-LBV8W3105KM123456",       // 本体：这辆车
  "actor": "QC-liuyang",               // 谁
  "车漆": "划痕",                       // 属性键 = 方面；值 = 该方面取到的状态
  "space": "左前门",                    // 时空戳：车辆参照系的命名区域（归时空树）
  "time": "2026-09-02T14:03:11+08:00", // 发生时间（结算时间由系统另记，互不冒充）
  "evidence": "img:defect-8821.jpg"    // 依据
}
```

端点不按 URL 分流；`type` 键路由到该类型的 schema 与规则。**一次发生可写多个 id 下的属性**（"一次发生、多处变化"，如批次绑定 VIN 同时写批次本体与车辆本体）。

**分解的边界判定**：同一名词在不同事实里归不同维度，由事实的意图决定——"左前门"在"划痕在哪"里是空间（车辆参照系的命名区域）；在"法规件追溯"（批次绑定）里是本体（有批次、有供应商、有质量承诺的制造件）。判据：这个事实上，它是被观察的存在，还是观察的坐标？

### 事件类型注册表 = 写侧 API 的全部定义

每行五列：

| 列 | 内容 | 例 |
|---|---|---|
| type | 事件类型名 | `ProductionReported` |
| 必填键 | schema 强制项（键须在字典登记） | `id, actor, qty, station` |
| 可选键 | schema 可选项 | `evidence, remark` |
| 适用规则 | 规则模块引用（属性谓词匹配） | "仅状态∈{已下达,开工中}的工单可报工" |
| 修正类型 | 对应的冲正/作废事件类型 | `ReportReversed` |

这张注册表同时是四样东西：**API 契约、校验依据、审计索引、LLM 工具清单**（function calling schema 从注册表自动生成）。

## 三、四层校验：错误在哪层被拦，以什么成本被拦

```
提交 → [0] 字典登记校验：所有键在本域属性字典中？未登记 → 系统不认识，拒绝（瞬时）
     → [1] 可聚合性校验：含 id 键？不含 → 无法落地，拒绝（形式错误，瞬时）
     → [2] 类型 schema 校验：必填键齐？该类型被授权写这些键？→ 拒绝（形式错误，瞬时）
     → [3] 规则过滤（决策环）：业务合法？不合法 → 候选废弃，返回违反的规则清单
                                          （零事件、零补偿、零污染）
     → 结算：append 进事件树 = FACT，返回事件 id
```

第 0–2 层是形式校验，同步返回；第 3 层是业务校验，走决策环（预演 → 规则过滤 → 结算），可同步可异步。**已呈现给观察者的序列永不修改；结算后发现错误，走修正类型事件。**

## 四、属性字典：按领域分治的词汇表

类被消灭了，schema 没有消失——它从"每类一张表"变成**每个子系统一本字典**。k-v 越自由，字典必须越严格，否则"按属性匹配"整套机制被同名异义、异名同义、单位漂移击垮。

**论域归属**：抽象层，"法"的家族成员——规则是法，**字典是法的词汇表**。羊皮纸原型 = 度量衡 / 编码规则本 / **会计科目表**（科目=属性、凭证=事件、账簿=本体；科目表的治理经验直接可搬）。

**方言与分治**：语义是领域的属性。`漆面`在家具域与汽车域是两种方言——跨域同名异义不是要消灭的 bug，是要尊重的现实。因此：

- **一个子系统一本字典**：域内键唯一、无歧义，使用时**省略前缀**（`漆面`）
- **跨域通信用全名**：`car.漆面` / `furniture.漆面`——基础设施不理解内容、语义只在端点，端点对话须带词典页码
- 领域前缀**不是类层级**：它不声明本体是什么，只声明词汇在哪里有效
- 跨域方言冲突不追求统一，追求**翻译**：域际适配层维护方言映射（海关，不是普通话推广委员会）
- 规模由此可控：无全局万级字典与中央委员会；子系统字典在千级以内，内部自洽即可

**条目最小字段集**：

| 字段 | 作用 |
|---|---|
| 键名 + 语义定义 | 消歧第一道防线 |
| 数据类型 + **单位** | 单位漂移是字典最常见的死因 |
| **值域** | 该方面可取的状态集合（例：`车漆` ∈ {完好, 划痕, 凹陷, 色差…}）——组合码在值域层被吸收 |
| 写授权 | 哪些事件类型允许写它（校验第 2 层执行） |
| 原生 / 派生 | 原生 = 事件直接写入；派生 = 规则推导（须引用推导规则） |
| 版本与弃用 | `deprecated` / `replaced_by` |

**字典缩水的路径**：西门子缺陷字典的三维组合码（方位码 × 部件码 × 故障模式码）在新模型里塌缩——方位码退出（归时空树：车身区域图），部件码退出（归本体或时空，按事实意图判定），故障模式拆为"属性名（方面）+ 值域（状态）"。最终字典条目只剩三样实质内容：**方面名 + 值域 + 单位与语义**。

**演化纪律**：键的语义只增不改；改语义 = 注册新键 + 弃用旧键，历史事件中的旧键永不改写。字典自身 append-only，与事件树同构。

## 五、时空维度：归时空树，字典的手伸不过去

时空是第一类维度，与属性正交，由世界模型架构的**时空树子系统**自治：锚点体系、多坐标系（含运动参照系）、精度分级、邻近判定、AS OF t。

- **本体有时空锚**：物理本体有位置/轨迹；契约本体有有效期（工单的有效区间即其时空属性）
- **事件有双时间**：发生时间（业务何时发生，可模糊、可回溯补录）与结算时间（系统何时落账），两者都记，互不冒充
- **时空参照三形态，精度分级**：绝对参照（坐标/精确时刻）→ 相对参照（"2 号工位东侧""左前门"——锚点相对定位）→ 模糊文本（"三点来钟""中段附近"）
- **模糊纪律**：原文照存（append-only，作为证据），能锚定的锚定，锚不定的标精度等级，留待后续解析；解析结果是另一个可修正属性，原文永不改写
- 查询按精度匹配：查"总装线"命中"总装线中段"，查"15:00–15:30"命中"三点来钟"

## 六、定义层：四个数据集合

**定义是数据，不是远程调用。** 定义动作（登记属性、事件类型、规则、视图）对上层业务开发暴露为**系统内部方法调用**；运行侧**启动时把四个数据集合整体加载进内存**，运行中由定义事件热更新——不走远程 API，避免每次启动的远程加载开销。

**四个数据集合本身是定义事件流的物化投影**：定义事件（`AttributeRegistered` 等）append 进定义事件树，fold 出这四个集合。启动加载 = 读投影快照；崩溃恢复 = 快照 + 定义日志重放——与运行时事件树同构。

定义动作的入口仍是候选-结算（自同构）：AI 或用户起草的定义在结算前只是**定义候选**，不生效；经规则校验（与既有键冲突？语义重叠？）加人工确认，结算为定义事实。**AI 的幻觉在定义层同样在架构上无法生效**——"LLM 不碰状态"铁律的第二次应用。

### 数据集合 ① 属性字典（AttributeDictionary）

```
AttributeEntry = ( key            // 键名，域内唯一；跨域全名 = domain.key
                 , semantic       // 语义定义（消歧的第一道防线）
                 , datatype       // 数据类型
                 , unit           // 单位（单位漂移是字典最常见的死因）
                 , range          // 值域：该方面可取的状态集合
                 , writers        // 写授权：允许写它的事件类型清单
                 , kind           // 原生（事件直写）| 派生（须含 rule_ref）
                 , rule_ref?      // 派生属性的推导规则引用
                 , status         // active | deprecated（replaced_by）
                 , version        // 版本；语义只增不改
                 , registered_by  // 登记事件 id（定义事实的引用）
                 )
```

### 数据集合 ② 事件类型注册表（EventTypeRegistry）

```
EventType = ( type            // 类型名
            , required_keys   // 必填键（字典引用）
            , optional_keys   // 可选键（字典引用）
            , rules           // 适用规则引用（校验第 3 层）
            , correction      // 修正类型引用（可空）
            , multi_target    // 是否允许一次发生写多个 id
            , settlement      // 同步 | 异步
            , status, version, registered_by
            )
```

### 数据集合 ③ 规则集（RuleSet）

```
Rule = ( rule_id
       , predicate      // 属性谓词：匹配条件（需要哪些键、值条件）——决定适用性
       , effect         // 过滤（合法性校验）| 推导（派生属性）| 触发（产生新事件候选）
       , logic          // 处理逻辑（确定性纯函数）
       , consumers      // 消费侧：写侧过滤 | 读侧渲染 | 两侧
       , status, version, registered_by
       )
```

覆盖验证：状态机 = 作用于状态属性的过滤规则族；工作流 = 前置链过滤规则；派生指标 = 推导规则；权限 = 对 actor 属性的过滤规则；报警升级 = 触发规则。**传统功能模块全部归约进本集合。**

### 数据集合 ④ 视图注册表（ViewRegistry）

```
ViewEntry = ( view_id
            , queries       // 事件类型清单 + 折叠规则 + 口径（L0/L1/L2）+ 时空切片
            , selects       // 键清单（字典引用；可跨本体、跨粒度）
            , rules         // 规则引用（决定行/列/按钮，与写侧同一份）
            , emits         // 可发起事件类型（②的子集引用）
            , render_mode   // 终态 | 流水 | 拦截
            , variants      // 角色预设（同一 view_id 的多套观察者配置）
            , status, version, registered_by
            )
```

### 加载与一致性纪律

1. **启动**：加载四集合的最新快照 + 规则产物库（已烘焙产物），**零编译、零远程调用** → 系统具备全部定义。
2. **运行中**：定义事件结算 → 四集合版本化热更新；事件/视图对新旧版本的引用显式携带版本号。
3. **引用完整性**：②③④ 中的键必须是①的已登记键（未登记 = 编译不过）；④的 emits 必须是②的已注册类型。
4. **四集合跨域不共享**：每域各载各的字典与注册表；跨域全名仅在信封出域时附加。

### 烘焙管线（编译是定义结算的一部分）

规则的源码到生效之间只有一条合法路径——烘焙管线，它是定义层内部方法调用的固定环节：

```
定义候选（规则源码 + deps 声明）
  → 编译：JS/TS → 沙盒字节码；或任意语言 → WASM 产物
  → 静态检查：deps 键在字典登记？类型/单位匹配？（字典兼任规则的编译期类型系统）
  → 沙盒试跑：样例输入单测
  → 结算：源码 + 产物 + 内容哈希 + 引擎版本 一并写入定义事件树
  → 热更新：四集合新版本生效
```

- **编译失败 = 定义候选被拒**，与业务候选被规则过滤同一条铁律
- **产物库内容寻址、append-only、永不删除**：按哈希存取——审计重放十年后仍能调出同一产物
- **启动零编译**：启动只加载产物快照；编译推迟到启动时是反模式（每次启动重新引入不确定性与延迟，编译错误在启动时爆炸）
- **引擎版本钉死**：结算记录 `def_versions` 含规则产物哈希 + 沙盒引擎版本——同产物 + 同引擎才有逐比特重放
- **产物唯一合法来源是烘焙管线**：开发者禁止手工放置产物；CI 可跑同一管线做预烘（提交前暴露问题），正式烘焙发生在定义结算时

## 七、所有入口殊途同归

| 入口 | 适配层职责 |
|---|---|
| 人工 UI（46 个视图的 emits 按钮） | 视图契约规定可发起的事件类型；按钮可用性由同一份规则渲染 |
| 扫码枪 / RFID 过点 | 设备适配器把物理动作翻译为变化描述 |
| PLC / 传感器 | 三层过滤（迟滞状态机 + 聚合网关）后，迁移沿成为候选——高频噪声到不了端点 |
| ERP / WMS / PLM | 系统适配器把外部报文翻译为变化描述（订单下达、库存变更） |
| LLM 自然语言指令 | LLM 适配器把"把 3 号工单调到 2 号产线"解析为变化描述；幻觉输出在规则过滤层被拦，**架构上无法成为事实** |

入口无限多，形状只有一个。新增入口 = 新增一个适配器，系统内核零改动。

## 八、读侧：视图注册表

每个视图 = 四元组契约的注册行：

```
View = ( queries   // 查询哪些事件类型 + 折叠规则（口径声明：L0/L1/L2；时空切片）
       , selects   // 从本体聚合集选择哪些键（可跨本体、跨粒度，无需 join；键须在字典登记）
       , rules     // 属性谓词匹配到的规则（决定行/列/按钮，与写侧同一份规则）
       , emits )   // 可发起的事件类型（= 写侧注册表的子集引用）
```

- 渲染模式三选一：终态 / 流水 / 拦截（见提取文档 4.3）
- 通用能力：`AS OF t` 时间回溯对所有视图生效；视图粒度是选择的结果，不是数据结构的前置约束
- 46 个视图的契约表 = 本注册的实例化（下一步交付物）

## 九、与架构地基的对应

| API 层概念 | 架构对应物 |
|---|---|
| 提交变化描述 | 迁移沿候选（决策环输入） |
| 四层校验 | 三层过滤 + 字典登记（L0 候选不污染事件树） |
| 结算 = FACT | 事实终局：append-only，不推翻；错误以新事实修正 |
| 单端点 + 自描述 payload | 信封（Envelope）：基础设施不理解内容，语义只在端点 |
| 时空戳 / 空间参照 | 时空索引树（锚点系统、AS OF t、精度分级） |
| 类型注册表挂规则 | 软逻辑流水线·规则步：读写两侧消费同一份规则 |
| 定义候选-结算 | 决策环机制的自举复用 |
| 四个数据集合（启动加载） | 定义事件流的物化投影：快照 + 热更新，恢复 = 快照 + 定义日志重放 |
