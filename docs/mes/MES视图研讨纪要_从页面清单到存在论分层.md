## 第〇章、概念地基：四个原语

（研讨最后收敛完成，置于篇首——后续所有章节都是它的展开。）

**四个原语，两个论域；原语不可再分，不由其他原语构成，只由原语之间的关系定义。**

| 原语 | 论域 | 定义 | 喻 |
|---|---|---|---|
| 本体 | 存在层 | 现实存在的数字句柄（id + k-v 属性聚合；无类、无继承，类型是属性集合的涌现形态；**聚合不互斥**——一个属性可属于多个本体） | 体 |
| 事件 | 存在层 | **本体的变化描述** | 变 |
| 规则 | 抽象层 | 按属性匹配本体的规范（属性谓词 + 处理逻辑） | 法 |
| 视图 | 抽象层 | 观察者对本体的切片 | 看 |

**构成性关系（共八条，无第五原语、无第九条关系）：**

- 事件：发生在本体上（被本体承载）；被规则过滤（合法才成事实）；被视图呈现（可观察）
- 本体：承载事件（被事件塑造）；被规则匹配；被视图观察
- 规则：约束事件（写侧）；约束视图（读侧）
- 视图：观察本体与事件；引用规则

**属性的多属与组合**：属性与本体是多对多——一个属性可属于多个本体（如耳朵、脑袋、人各自是本体，属性沿组合链多属）。**部分-整体 = 属性集合的包含关系，不是类型继承**：整体本体注册时其聚合集包含部分的属性；组合是实例间的属性集包含，依然无类。推论：①无封装——事件写入某属性，所有聚合集包含该属性的本体观察面同时变化（"可被多方面观察"的机制：观察粒度自由，共享属性在每个粒度都在场）；②规则按属性匹配，天然跨粒度生效；③整体层的派生量（总体重、总产量）由规则从共享属性推导，产物仍是普通属性，仍可被多本体聚合。车间对应：工位完成一件，属性变化同时在工位/产线/车间三个本体的观察面就位——"层层汇总"的统计口径，本质全是属性多属。

**三条硬结论**：

1. **没有自由漂浮的事件——但校验的是"可聚合性"，不是"引用字段"**：事件 = 属性变化的描述，本体锚定不立特权字段——变化集中包含 id 键（本体的内核属性），变化即自然聚合到该本体；不含 id 键的变化描述无法 fold 进任何 k-v 集合，不予结算。一切皆属性：本体的诞生是首个携带某 id 键的事件（无独立 create 操作）；因果与修正是普通键（`corrects: 原事件id`）；多本体参与是"一次发生、多处变化"（一个事件可写多个 id 下的属性）。
2. **体先于变（不对称性）**：本体可以暂无变化（沉睡本体合法）；变化描述必须可聚合到某个体（无对象的变不成立）。
3. **修正机制的纯洁性**：修正事件描述属性的**再次变化**，并以普通属性携带对原事件的引用。**被修正的从来不是事件，而是本体的属性值；事件只被引用，不被改变**——因为事件不是"体"，它不能成为"变"的对象。事件树 append-only 与本体属性演化，两层各守其位。

## 起点问题

研讨从一个具体问题开始：**从最终落地视角，MES 系统有多少种列表视图、多少种内容视图？** 最终它没有停留在清单层面，而是逐层下钻，终点是一套可检验的概念架构。以下是逐阶段的结论。

---

## 一、行业盘点：视图的枚举层结论

MES 列表视图可归为 6 大类：**生产执行**（工单/排产/工序任务）、**资源**（设备/人员/工装）、**物料与追溯**（物料/BOM/批次/WIP）、**质量**（检验/不合格品）、**异常与事件**（报警/停机/报工记录）、**统计报表**。

详情视图 5 大类：**工单详情**（头-行结构）、**追溯详情**（正反向谱系）、**设备画像**（状态+参数+历史+OEE）、**质量详情**（检验单/SPC）、**主数据档案**。另有灰色地带：看板/驾驶舱（聚合视图）。

实践观察：页面膨胀的根源不在类型而在**变体**——同一列表，计划员、班组长、操作工看到的列、筛选、操作不同。解法是"一个列表 + 多套角色视图配置"，而非多套页面。

---

## 二、概念抽象：视图是什么

从 MES 业务往下抽，视图的本质定义：

> **视图 = 观察者为了支撑一个决策，对世界状态做的一次切片。**

**四个性质**：选择性（永非全量）、视角性（观察者相对）、派生性（可丢弃可重建，非真相本身）、目的性（每个元素可追溯到决策：筛选=关注域，列=输入参数，操作=输出出口）。

**原子切法只有四种**（世界是"实体 × 时间 × 关系"张成的）：

| 切法 | 视图形态 | 回答 |
|---|---|---|
| 横切（固定时间，跨实体） | 列表视图 | 此刻哪些对象处于什么状态 |
| 纵切（固定实体，沿时间） | 详情视图 | 这个对象经历了什么 |
| 遍历（沿关系边游走） | 追溯视图 | 它与谁相连、从何而来 |
| 上卷（跨实体×时间聚合） | 看板/报表 | 总体怎么样（有损，不可再下钻） |

**视图之间靠组合与转移构成导航图**：组合（详情内嵌子列表，视图可递归）、下钻（列表→详情，参数 entityId）、跳转（沿关系边→另一实体详情）、上卷（聚合→看板）。导航 = 视图之间的转移函数。

**视图与操作的对偶**：视图只读；操作不生成视图，操作改变世界，世界再投影出新视图。操作栖身于视图但逻辑上不属于视图——写通道与读通道通过世界状态间接耦合，永不直接耦合。

**数量的生成式回答**：视图总数 = 4 种切法 × N 个业务对象 × M 种观察者角色。切法与对象可枚举、应预置；角色是配置，不产生新页面。

## 三、案例验证：西门子整车厂 46 个视图

对《西门子助力打造数字化汽车工厂》（63 页售前方案，覆盖冲压/车身/涂装/总装，含计划、物料、AVI、ANDON、PMC、质量、设备七模块）做了完整视图提取，共 **46 个视图**：横切 19（41%）、纵切 9（20%）、上卷 11（24%）、遍历 3（7%）、配置/建模 4（9%）。

关键发现：

1. **整车厂视图的锚点是 VIN**——纵切与遍历几乎都以"一辆车"为中心（单件流）；车间类型决定视图的默认锚点（机加/电子则以批次/工单为锚）。
2. **A3 作业计划五状态队列**是"状态机决定视图操作"的教科书样本：操作权限随状态收敛（01/02 可调 → 03/04 退回再调 → 05 绝对禁止）。
3. 四种切法之外发现一个正交维度：**操作型视图**（防错校验、缺陷采集）——目的不是展示，而是拦截错误动作。
4. **遍历视图仅 3 个但权重极高**（法规件追溯、缺陷车辆不出厂）——数量与业务价值倒挂。
5. 从售前材料提取视图须区分"业务上不存在"与"材料未披露"（工单详情、设备详情属后者）。

## 四、视图—事件对账：从"页面"到"契约"

**三条对账原则**：

1. **视图不存状态**：视图 = 截至 t 时刻对事件树的查询结果（AS OF t 的 fold）。"当前时间"只是 t = now 的特例。
2. **操作不产生修改，只产生事件**："修改/删除/调整"落到系统里都是 append。UI 词汇表中的"编辑/删除"应替换为业务动作词汇——撤销、冲正、变更、作废，每个都是新事件类型。
3. **纠错是另一个事件**：不触碰原事件，追加修正事件；原事件永存，视图投影自然算出终态。

**事件世界三层**（视图须声明查询口径）：L0 候选（未结算，被拦截的输入，不进事件树）、L1 事实（已结算，默认查询对象）、L2 修正（追加事实；终态视图显示修正后的值，流水视图原事件与修正同列可见）。

**三种渲染模式**（与切法正交）：终态模式（横切默认）、流水模式（纵切/记录类列表，冲正成对可见）、拦截模式（操作型视图，主角是未结算候选的即时反馈）。

**每个视图的定义升级为四元组契约**：

```
View = ( queries   // 查询哪些事件类型 + 折叠规则
       , selects   // 从本体选择哪些属性键
       , rules     // 对本体的 k-v 求值属性谓词所匹配到的规则
       , emits )   // 可发起哪些事件类型
```

## 五、构建链：先有视图，再有属性

**方向感：设计时反向，运行时正向。**

- 设计时（需求反推）：视图定义（谁、为了什么决策）→ 属性需求 → 事件载荷需求 → 采集需求（现场布什么传感器/扫码点）
- 运行时（数据正向）：事件 → 提取规则（fold）→ 本体属性 → 视图按定义选择 → 渲染

**纪律一：属性共享，视图只选不提。** 属性的可能性全集由写侧定义（事件类型可写入的键的并集），物化必要集由读侧定义（视图需求并集）。视图私自提取属性 = 同一状态两个值，投影架构最典型的病。未被任何视图需要的属性不物化，按需回放计算（惰性）。

**纪律二：规则一份定义，两处消费。** 写侧（规则模块过滤候选事件）与读侧（视图构建：行过滤、列可见、按钮可用）消费同一份规则。视图只消费规则步，不消费价值/意图步。**架构性质：界面上能点的操作与系统能结算的事件数学上一致**——"按钮灰了但 API 能调"这类 bug 在结构上不可能出现。

---

## 六、本体论澄清：没有类

研讨中一次重要的概念纠错：

- **本体 = 唯一 id（句柄/内核/引用）+ k-v 属性聚合。没有类，没有类型声明，没有继承。**
- 本体"是什么"不由类型归属决定，而由它实际聚合了哪些属性决定。"车辆""设备"是属性集合的**涌现形态**，不是先验类型。
- **规则按属性匹配，不按类型归属**：规则 = 属性谓词 + 处理逻辑；本体拥有对应属性，规则即可处理它。
- 演化因此免费：给本体追加属性（新事件写入新 k-v），它自动进入所有匹配规则的射程——无需改 schema、无需迁移。

---

## 七、存在论分层：两个论域

**本体、规则、视图分属两个论域，不可通约：**

| 层 | 成员 | 判据 |
|---|---|---|
| 存在层 | 本体（存在的"体"）、事件（存在的"变"） | 现实中有孪生体，可被多方面观察 |
| 抽象层 | 规则、视图 | 无现实孪生体，删除后车间不受任何影响 |

- **本体是存在的事物**：现实中有孪生体；id 是现实事物的数字句柄；k-v 是可观察面，不是本体本身。本体不是逻辑游戏，是描述真实存在的现实的。
- **规则与视图形似而本质不同**：规则是**规范性**的（法：无观察者、普遍适用、约束可能性空间、写侧消费）；视图是**认识性**的（看：必有观察者、观察者相对、取可能性空间的截面、读侧消费）。法不因谁看而改变；看永远不改变世界本身。

**分类检验（两问）**：①它在现实中有孪生体吗？②删掉它，世界变不变？（视图删了世界不变，规则删了行为变，本体句柄删了系统失明。）

**羊皮纸测试（历史回溯检验）**：问"一百年前它是什么？"工单是契约——前数字化时代是羊皮上的文字，客观存在。判据不是载体本身，而是**是否绑定具体存在**：工单写"这一批活"（具体，存在层）；规程写"所有这类"（普遍，抽象层）。

四层的历史原型：本体=实物+契约文书；事件=纸上的章与签字；修正事件=会计红字冲销；规则=制度汇编；视图=车间黑板（可擦写，擦掉不算篡改历史）。

**核心推论**：事实终局不是计算机科学的发明，是账房纪律的再发现——"落章不可刮、冲正用红字"。数字化的本质不是发明新东西，是给四种早已存在的东西换载体，并第一次让它们机器可读、可审计。沟通话术由此而来：这套系统不是把车间变成数据库，是把车间恢复成它本来的样子。

## 八、最终概念栈（一张图）

```
抽象层  │  视图（看：认识性）── 规则（法：规范性）
        │    │ queries/selects    │ 属性谓词匹配
        │    ▼                    ▼
存在层  │  本体（体：id + k-v）◄── 事件（变：append-only）
        │    ▲ 现实孪生体的句柄     ▲ 真实变化的记录
        └────┴────────────────────┴──────────
             依赖单向无环：事件写属性，属性被规则匹配，视图引用三者
```

四层各自可独立演化：加属性、加规则、加视图，都不需要回头改旧定义。任何新概念进系统前先过两问检验与羊皮纸测试——过不了存在层检验的，永不许注册为本体、永不许进事件树。这保证事件树的纯洁性：每条都是真实发生过的事，没有一条是系统内部 bookkeeping 的私货。

## 九、API 与定义层：事件即接口

概念地基向工程形态收敛的结论（详见《系统API设计_事件即接口》v2）：

1. **两个动词**：写 = 提交变化描述（`POST /events`），读 = 求值视图。无 update/delete（违背事实终局），无版本号（演化即注册新事件类型，append-only）。
2. **事件原子形态**：某本体的某属性，在某时空，变成了某值。payload 最小内核 = `{id, 属性键, 新值}` + 时空戳。
3. **四维分解，各归各的治理**：本体→注册机制；属性→属性字典；值→条目值域；时空→时空树子系统。同一名词在不同事实归不同维度，由事实意图判定（左前门：缺陷定位中是空间，法规件追溯中是本体）。
4. **属性字典按领域分治**：语义是领域的属性，方言（`car.漆面` / `furniture.漆面`）要尊重不要消灭；一子系统一本字典、域内省略前缀、跨域用全名、冲突靠翻译不靠统一。领域前缀 ≠ 类层级（前者声明词汇在哪里有效，后者声明本体是什么——已消灭）。
5. **字典条目最终只剩三样实质**：方面名 + 值域 + 单位与语义。组合码塌缩：方位码归时空树（车身区域图），部件码归本体或时空，故障模式拆为属性名+值域。
6. **校验四层**：字典登记 → 可聚合性 → 类型 schema → 规则过滤。
7. **定义层与运行层自同构**：字典管理模块 = 系统定义的符号表（事件类型/视图/本体聚合集三张注册表的键均须字典登记，未登记=编译不过）；定义也走候选-结算（AI 起草的定义未结算不生效——"LLM 不碰状态"铁律在定义层的第二次应用）。

## 十、后续行动

1. **46 视图契约表**：逐个填四元组（queries / selects / rules / emits），每个引用先过存在性检验——这是产品设计与世界模型内核之间的正式接口文档。建议从 A3（五状态队列）或 F11（返修流转）打样。
2. **车间验证矩阵**：业务场景 × 不变量（无回滚、重放逐比特一致、事件率有界、无全局时钟）——"世界模型在车间有效"的操作化定义。
3. 车间能证明"域架构在原理上成立"（M0–M2、M4、M5），证明不了"规模上划算"（M3 密度、M6 生态）——前者是证伪性问题，车间够用；后者需园区级场景。
