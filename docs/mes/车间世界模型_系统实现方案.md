## 二、核心数据形态

### 2.1 事件（运行时）

```
Event = ( event_id        // 结算时分配，域内单调
        , type            // 事件类型（注册表引用）
        , writes          // {id: {属性键: 新值, ...}, ...}——一次发生可写多个本体
        , spacetime       // {space: 锚点/坐标/模糊文本, occur_time, precision}
        , actor           // 发起者本体 id
        , evidence?       // 依据（扫描原始值、图片哈希、外部单号）
        , corrects?       // 因果引用：原事件 id
        , settle_time     // 结算时间（逻辑时钟戳）
        , def_versions    // 结算时使用的四集合版本号（审计重放的锚）
        )
```

**铁律**：append-only；已结算事件永不修改；`def_versions` 使任何决策可在符号层逐比特重放。

### 2.2 本体投影（运行时）

```
Ontology = ( id
           , attrs        // {属性键: (值, 来源事件id, 版本)}——fold 结果
           , aggregates   // 聚合集声明：本 id 聚合哪些属性键（可含他本体写入的键）
           , anchors      // 时空锚引用
           , last_event_id
           )
```

fold 以**属性为单位**：事件写入一个键，所有聚合集包含该键的本体观察面同时更新（多属的实现机制）。

### 2.3 快照

定距增量快照：每 10000 事件或 300s（先到为准），写时复制只存变化区域；事件高发区域自动加密。`AS OF t = 最近前置快照 + (t₀, t] 事件增量重放`，目标延迟 < 50ms。

## 三、组件设计

### 3.1 事件日志

- 单车间单域起步：**一个分区一根日志**，域内全序
- 选型：PostgreSQL（分区表 + 追加写 + 逻辑序号）即可支撑车间级事件率；备选 EventStoreDB；不上 Kafka（本期无跨域路由需求，M2 再引入）
- 事件体不可变；索引：`(id, settle_seq)`、`(type)`、`(corrects)`、`时空索引外键`

### 3.2 决策环与四层校验

- 第 0–2 层（字典登记 / 可聚合性 / 类型 schema）：同步、微秒级、纯内存查表（四集合已加载）
- 第 3 层规则过滤：预演在内存沙盒进行——候选+当前投影副本→规则求值；**不通过即内存回收，零事件零补偿**
- 结算：单写者（单域串行结算器）保证域内全序，无锁
- 同步/异步边界：类型注册表的 `settlement` 字段决定；操作型视图（防错拦截）要求同步返回

### 3.3 规则引擎

**规则是代码，但代码运行在无环境沙盒里。** 语言中立：JS/TS（QuickJS / V8 isolate）或 WASM（任意语言编译嵌入）均可；宿主契约相同——剥离全部全局对象：无时钟、无随机数、无网络、无文件、无数据库、无环境变量。**ambient authority 是确定性与可审计性的死敌。**

- **唯一能力：读声明过的字典属性。** 规则的 `deps` 声明即属性谓词；引擎按声明注入本体属性（依赖注入），未声明的键对规则不可见（最小权限）
- **静态检查**：deps 引用的键必须在属性字典登记——编译期即可发现未登记键与单位不匹配；字典同时充当规则代码的类型系统
- **依赖图红利**：deps 声明使派生属性的重算时机、键变化的影响面全部静态可知，无需运行时追踪
- 签名：`eval(attrs, candidate) → 通过/拒绝+理由 | 派生值 | 触发新候选`——attrs 只含声明的键，candidate 为提交的变化描述
- **烘焙管线**（编译是定义结算的一部分，见 API 文档第六章）：源码 → 编译（字节码/WASM）→ 静态检查 → 沙盒试跑 → 结算（源码+产物+哈希+引擎版本入定义事件树）→ 热更新。**产物库内容寻址、append-only、永不删除；启动零编译，只加载产物快照**
- **版本钉死**：事件结算时记录规则产物哈希 + 沙盒引擎版本（`def_versions`）——同产物 + 同引擎，才有逐比特重放
- tie-break 用确定性纯函数（安全优先级、id 字典序）

### 3.4 投影引擎

- 订阅事件日志，逐事件 fold 到本体投影、时空树、因果边表
- 投影可丢弃可重建；`last_event_id` 支持增量重建与落后量监控
- 惰性：无订阅者的本体投影冻结，索引保留条目，事件唤醒

### 3.5 定义层（四集合）

- 物理形态：定义事件流（与运行时事件同一存储、独立分区）+ 四集合物化投影
- **启动：加载四集合快照，零远程调用**；运行中：定义事件结算 → 版本化热更新
- 引用完整性在定义结算时强校验：②③④ 的键必须在①登记，④的 emits 必须在②注册
- 定义入口对业务开发暴露为**内部方法调用**（SDK），非远程 API

### 3.6 时空树子系统

- 锚点表：命名锚点（车间/产线/工位/区域）+ 坐标系定义（含运动参照系：车辆=移动参照系，车身区域=其命名区域图）
- 空间索引：R-tree（车间尺度足够；PostGIS 或内存 R-tree）
- 三形态参照的统一存储：`{anchor_ref | coord | raw_text, precision}`——**模糊原文永不改写**，解析结果为独立可修正属性
- 向事件日志与视图引擎提供：`AS OF t`、区域内查询、精度匹配（"总装线"命中"总装线中段"）

### 3.7 视图引擎

- 求值四元组：`queries`（事件查询+fold 口径）→ `selects`（跨本体取键，无 join）→ `rules`（行/列/按钮过滤）→ 渲染模式（终态/流水/拦截）
- 观察者上下文（角色）= `variants` 预设选择
- 46 视图契约表即本引擎的注册数据（见开发说明文档）

### 3.8 API 层

- 两个动词：`POST /events`、`GET /views/{viewId}`
- 幂等：候选层幂等键（来源方生成），重复提交返回原回执
- 鉴权与信任分级：PLC 网关 / 人工 UI / 外部系统分凭证等级

### 3.9 适配层

- 每个入口一个适配器，职责唯一：**把外部信号翻译成变化描述**
- PLC/传感器侧前置三层过滤（迟滞状态机 + 聚合网关），噪声到不了端点
- LLM 适配器：function schema 从事件类型注册表自动生成；输出只是候选，规则过滤兜底

## 四、技术选型建议

| 组件 | 建议 | 理由 | 备选 |
|---|---|---|---|
| 语言 | Go 或 Rust | 单写者结算器、投影引擎需要高并发与确定性 | Java（团队熟悉优先） |
| 事件存储 | PostgreSQL 分区表 | 车间级事件率（10²–10³/s）富余；运维简单 | EventStoreDB |
| 投影/四集合 | 内存为主 + 快照落盘 | 启动加载语义；查询微秒级 | Redis（不建议：丢失 fold 控制权） |
| 规则沙盒 | 表达式 DSL（自研）或 Lua | 确定性、可审计 | WASM |
| 时空索引 | 内存 R-tree + 锚点表 | 车间尺度小 | PostGIS |
| UI | 视图引擎输出 JSON，前端渲染器按渲染模式通用实现 | 视图即数据，前端无业务逻辑 | — |

## 五、非功能指标（车间级验收）

| 指标 | 目标 |
|---|---|
| 事件结算吞吐 | ≥ 1000 events/s（单域单写者） |
| 四层校验同步返回 | P99 < 50ms |
| AS OF t 查询 | < 50ms（快照+增量重放） |
| 重放逐比特一致 | 同输入重放 3 次，投影哈希一致（最硬指标） |
| 崩溃恢复 | 快照 + 日志重放 < 60s |
| 噪声洪峰 | 传感器噪声注入下事件率有界（三层过滤验证） |

## 六、实施路线（车间裁剪版）

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0 最小细胞 | 事件日志 + 四层校验 + 决策环 + 单视图投影 | 重放逐比特一致 |
| P1 定义层 | 四集合 + 启动加载 + 定义候选-结算 + 热更新 | 定义变更不停机生效 |
| P2 业务打样 | 字典初版 + A3/F11 契约表 + 视图引擎 | 两个视图端到端跑通 |
| P3 时空树 | 锚点/参照系/模糊文本/AS OF t | AVI 式位置跟踪 + 时间回溯 |
| P4 适配层 | 扫码/RFID + PLC 网关（三层过滤）+ LLM 适配器 | 噪声洪峰下事件率有界 |
| P5 审计闭环 | 决策级重放、修正事件链完整 | 审计重放与在线判定逐比特一致 |

全局基础设施（跨域路由、订阅分级、多租户）从 M2 以后再说——本期不需要，不提前建设。

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| 偷偷中心化（单库自增 ID 解决一切，架构主张未被验证） | 对抗性测试：注入延迟/分区；静态检查结算路径不读物理时钟与全局序号 |
| 字典治理失序（同名异义、单位漂移） | 第 0 层校验机械化 + 定义评审流程 + 键语义只增不改 |
| 规则膨胀失控 | 规则即代码：评审、单测、版本化；规则引用可追溯 |
| 视图引擎变成新的"业务逻辑垃圾桶" | 红线：视图只读、逻辑只在规则集；视图引擎无任何写路径 |
