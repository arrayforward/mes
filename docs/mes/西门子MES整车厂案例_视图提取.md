# 西门子 MES 整车厂案例：视图提取（v7）

> **来源**：《西门子助力打造数字化汽车工厂——SFAE MES》（2015.11，63 页售前方案）
> **场景**：整车厂，覆盖冲压、车身（焊装）、涂装、总装四大车间
> **提取口径**：视图 = 观察者为了支撑一个决策，对世界状态做的一次切片
> **归类方法**：四种原子切法——**横切**（固定时间，跨实体）、**纵切**（固定实体，沿时间）、**遍历**（沿关系边游走）、**上卷**（跨实体×跨时间聚合）
> **说明**：源文档为售前胶片，多数界面以功能点形式描述，视图按功能反推；少量无直接描述但功能上必然存在的视图标注为【推断】
>
> **v2 增补**：增加第四章"视图—事件对账"。核心对齐结论——视图不存状态，是截至 t 时刻对事件树的查询；用户在视图上的任何"修改/删除"都是向事件树追加新事件；纠错是另一个事件而非对原事件的修补。
>
> **v3 增补**：增加 4.5"构建链"。核心结论——先有视图再有属性（设计时反向反推、运行时正向投影）；属性提取是共享投影，视图只选不提；业务规则一份定义、两处消费（写侧过滤候选事件、读侧构建视图），使"界面上能点的操作"与"系统能结算的事件"数学上一致。
>
> **v4 修订（重要）**：纠正 v3 引入的错误概念。**本体没有"类"**：本体 = 唯一 id（句柄/内核）+ k-v 属性聚合。规则不挂在类上，而是声明自己处理的属性签名——本体拥有对应属性，规则即可处理它（按属性存在性匹配，非按类型归属）。"车辆""设备"等概念是属性集合的涌现形态，不是先验类型。
>
> **v5 增补**：增加 4.6"存在论分层"。核心结论——本体属于**存在层**（现实中有孪生体、可被多方面观察；id 是现实事物的数字句柄；事件是本体身上真实发生的变化，与本体同属存在层：体与变）；规则与视图属于**抽象层**（无现实孪生体）：规则是规范性的（无观察者、普遍适用、约束可能性空间），视图是认识性的（必有观察者、观察者相对、从可能性空间取截面）。二者形似而本质不同。
>
> **v6 增补**：4.6 增加"羊皮纸测试"。工单是契约——前数字化时代是羊皮上的文字，客观存在。分类检验的历史版：问"一百年前它是什么"，有具体载体（这张单、这枚章）→ 存在层；只有普遍陈述或易擦写呈现 → 抽象层。判据不是载体本身，而是**是否绑定具体存在**。事实终局 = 账房纪律"落章不可刮、冲正用红字"的再发现。
>
> **v7 修订（四原语地基回审）**：按最终概念地基全面回审。①4.2 改写"载荷四要素"——事件 = 属性变化的描述，**无特权字段**：actor、目标、因果引用、依据全是普通键；事件类型 schema = 必填键+可选键；结算层校验的是**可聚合性**（变化集含 id 键），不是引用关系。②本体诞生即事件（首个携带某 id 键的变化描述即注册，系统无独立 create）。③4.5 运行时链路体现**属性多属**：聚合不互斥，一属性可属多本体，部分-整体 = 聚合集包含关系，fold 以属性为单位、写入一次多粒度就位。④新增 4.7"属性多属对 46 视图的再审视"：建模视图 = 聚合集声明界面（非树编辑）；上卷/汇总 = 属性多属 + 规则推导；跨本体取值无需 join。结论不变：46 个视图无需增删。

## 三、观察与结论

### 1. 整车厂视图的锚点是 VIN——纵切和遍历都以"一辆车"为中心

总装是单件流，一车一档案。A4 工位指导、F7 车辆参数、F8 随车卡、F9 位置历史、F12 质量记录全部是**以 VIN 为主键的纵切**；B5、F14 两个遍历视图也都从 VIN 出发。这与机加/电子装配（以批次/工单为锚）形成鲜明对比——**车间类型决定视图的默认锚点**。

### 2. A3 是"状态机决定视图"的教科书样本

作业计划五状态（01–05）直接决定每行记录允许的操作：可调整 → 须退回 → 绝对禁止。视图上的操作按钮就是状态机的投影，与我们前面的抽象完全吻合。

### 3. 操作型视图是一个独立品种

B4 防错校验、F10 缺陷采集、F8 随车卡——这类视图的主要目的不是"展示"，而是**拦截错误动作 / 引导正确动作**。它们字段极少、反馈极快（扫码即报警）、容错设计重（下拉快速登记）。在四种切法之外，值得作为"按目的分类"的一个正交维度单独对待。

### 4. 看板类（上卷）占比 24%，且实时性分级明显

安灯大屏（秒级、现场、红绿黄）→ PMC 监控（实时、远程）→ 效率/质量报表（班次/日级、管理层）。同一个"上卷"，实时性、受众、载体（LED 大屏/PC/Web）完全不同，实际是三个亚种。

### 5. 配置/建模视图被严重低估

售前胶片把"动态图形建模"当卖点（I1/I2），F1–F6、F15 也都是配置视图——**近一成的视图在建模和配置**。这正对应我们之前说的"工厂模型"：车间布局、缺陷字典、检验计划、报警规则都是世界模型的本体层，这些视图本质是**本体的编辑界面**。

### 6. 遍历视图数量少（3 个）但权重极高

B5 和 F14 承载了"法规件追溯""缺陷车辆不出厂"（P68 宝马案例的核心承诺）这类最硬的需求。数量上 7%，业务价值上是最重的一类——遍历视图是 MES 区别于 ERP 的标志性视图，这一案例再次验证。

### 7. 对视图清单完整性的交叉验证

按最初讨论的 5 大类列表 + 5 大类详情对照：本案例覆盖了生产执行、资源、物料追溯、质量、异常事件、统计报表全部六类列表；详情侧覆盖工单（弱）、设备（弱）、物料/BOM、车辆档案（极强）、质量单（强）。**缺口在工单详情与设备详情**——不是西门子没有，而是售前胶片没展开，提取时已标注【推断】。这提醒我们：从售前材料提取视图时，需要区分"业务上不存在"与"材料未披露"。

## 四、视图—事件对账（v2 增补）

### 4.1 三条对账原则

**原则一：视图不存状态。**
视图 = 截至 t 时刻对事件树的查询结果（AS OF t 的 fold）。"当前时间"只是 t = now 的特例。横切渲染 fold 后的**终态**；纵切渲染**事件流本身**；遍历渲染事件间的**因果/谱系边**；上卷渲染 fold 后的**聚合**。视图可丢弃、可重建，身上没有一滴真相。

**原则二：操作不产生修改，只产生事件。**
用户在视图上的任何动作——下达、调整、删除、报工、登记缺陷——落到系统里都是 append 一个新事件进事件树。UI 词汇表中的"编辑/删除"应从产品语言中移除，替换为业务动作词汇：**撤销、冲正、变更、作废**——每一个都是新事件类型。

**原则三：纠错是另一个事件。**
输入错误的纠正不触碰原事件，追加修正事件。原事件永存，视图投影自然算出修正后的终态，历史痕迹完整。事件世界因此有三层，视图的查询口径必须声明自己查哪一层：

| 层 | 名称 | 说明 | 视图中的表现 |
|---|---|---|---|
| L0 | 候选（未结算） | 未通过校验、被拦截的输入（如扫码不匹配） | 只在操作型视图中即时反馈，不进事件树 |
| L1 | 事实（已结算） | 通过校验、正式 append 的事件 | 所有视图的默认查询对象 |
| L2 | 修正（追加事实） | 针对 L1 某事件的冲正/复核/作废 | 终态视图显示修正后的值；流水视图原事件与修正事件**同列可见** |

### 4.2 操作 → 事件映射（按模块）

每个视图上的操作按钮 = 一个事件类型定义。**事件 = 属性变化的描述，无特权字段**：谁（actor 的 id）、发生在谁身上（目标本体的 id）、做了什么、因果引用（`corrects: 原事件id`）、依据——全部是普通键。事件类型的 schema = 必填键 + 可选键清单。本体锚定从 id 键**涌现**：变化集含 id 键即可聚合到该本体；不含 id 键的变化无法 fold 进任何聚合集，不予结算——结算层校验的是**可聚合性**，不是"引用关系"。本体的诞生同样是事件：首个携带某 id 键的变化描述即注册，**系统无独立 create 操作**。

**A 生产计划管理**

| 视图操作 | 事件类型 | 对应修正事件 |
|---|---|---|
| A1 接收 / 删除 / 重接收 | `OrderReceived` / `OrderRevoked` / `OrderReReceived` | 误撤单 → `OrderRevokeReversed`（恢复） |
| A2 冻结 / 撤单 / 插单 / 换单 / 序列调整 | `OrderFrozen` / `OrderCancelled` / `OrderInserted` / `OrderSwapped` / `SequenceAdjusted` | 误操作 → 对应的逆事件（新事实，非撤销） |
| A3 五状态迁移（01→05） | `PlanReleased`（携带源状态、目标状态） | 03/04 的"退回 01"本身即新事件 `PlanRolledBack`；05 不可调整 = 状态机拒绝生成候选 |
| A7 完工报工 | `ProductionReported`（车身种类、时间、数量） | 报工错误 → `ReportReversed`（冲正）+ 新的 `ProductionReported` |

**B 物料管理**

| 视图操作 | 事件类型 | 对应修正事件 |
|---|---|---|
| B4 扫码比对通过 | `MaterialVerified` | ——（通过即事实） |
| B4 扫码不匹配报警 | **候选层事件，不结算**（仅即时拦截反馈） | 无需修正：未入树，零污染 |
| B5 批次与 VIN 绑定 | `BatchBoundToVIN` | 绑错车 → `BindingVoided` + 重新绑定事件 |
| B6 缺料呼叫 / 响应 | `MaterialCallRaised` / `MaterialCallAnswered` | 误呼叫 → `CallCancelled` |
| B7–B10 四类拉动单创建 / 发货 / 收货 | `PullOrderCreated` / `PullOrderShipped` / `PullOrderReceived`（按 Andon/Kanban/紧急/JIS/JIT 分子类） | 误发拉动 → `PullOrderCancelled` |

**C AVI**：`VehicleEnteredZone` / `VehicleExitedZone`（过点事件，RFID/扫描触发）。漏扫/误扫 → 补录事件 `PassageCorrected`，时间戳以事件记录为准，不改原序列。

**D ANDON**：`CallRaised` / `CallAcknowledged` / `LineStopped` / `LineResumed`。误拉绳 → `CallCancelled`（但停线事实若已发生则永存，以恢复事件表达终态）。

**E PMC**：`FaultAlarmed` / `FaultCleared` / `CountUpdated`。设备高频信号须经迟滞过滤成迁移沿后才成为候选——误报在 L0 被拦，修正事件频率因此天然有界。

**F 质量管理**（事件最密的模块）

| 视图操作 | 事件类型 | 对应修正事件 |
|---|---|---|
| F10 缺陷登记 | `DefectRegistered`（VIN、方位码、部件码、故障模式码） | 误录 → `DefectCancelled` |
| F11 返修五步流转 | `ReworkRequested` → `ReworkRecorded` → `ReworkSubmitted` → `RecheckJudged(OK/NOK)` → `ReworkClosed` | 误判 NOK → `JudgementOverruled`（复核改判，原判永存） |
| F12 检验设备数据写入 | `InspectionDataRecorded` | 设备误传 → `InspectionDataCorrected` |
| F13 车辆锁定 / 解锁 | `VehicleLocked` / `VehicleUnlocked` | 误锁 → `VehicleUnlocked`（锁定史永存，可追溯"谁锁的、锁了多久"） |
| F15 报警逐级升级 | `AlarmEscalated`（级别、责任人） | 规则误配导致的误升级 → 修规则（配置事件）+ `AlarmAcknowledged` |

**配置类视图（F1–F6、F15 规则、I1–I2）**：配置变更同样是事件——`OntologyChanged`（缺陷字典修订、检验计划改版、车间布局调整），版本化，影响其**之后**的事件解释，不回溯改写历史事件的语义。建模类视图（F5、I1）的 emits 本质是**注册/变更本体的聚合集**——车间→区域→工位的层级不是一棵需要单独维护的树，是聚合集的层层包含（见 4.7）。

### 4.3 对 46 个视图的回改要求

**（1）每个视图增补两项元数据：**
- `queries`：本视图查询的事件集合（事件类型清单 + 折叠规则）
- `emits`：本视图可发起的事件类型清单（即操作按钮的正式定义）

**（2）确立三种渲染模式，与切法正交：**

| 渲染模式 | 默认用于 | 行为 |
|---|---|---|
| 终态模式 | 横切（A3 队列、B3 库存、F13 锁定列表） | 显示 fold 后的当前值；修正事件不可见，只见其结果 |
| 流水模式 | 纵切（F9 位置历史、F11 返修记录、A7 报工记录） | 原事件与修正事件同列逐条可见，冲正成对出现 |
| 拦截模式 | 操作型视图（B4、F10） | 主角是 L0 候选的即时反馈；已结算事实退居背景 |

**（3）导航转移函数的参数不变，语义升级**：下钻（列表 → 详情）传的是 entityId + 事件查询口径；时间回溯（AS OF t）成为所有视图的通用能力而非特例功能。

### 4.4 与概念层的对齐检查

| 概念层性质 | 事件对账后的落实 |
|---|---|
| 派生性（视图可丢弃重建） | ✔ 视图 = 事件树的查询，重建即重放 |
| 视角性（观察者相对） | ✔ 同一事件树，不同 queries 参数 |
| 目的性（为决策服务） | ✔ emits 清单 = 该视图支撑的决策出口 |
| 操作与视图的对偶（只读视图 + 独立写通道） | ✔ 写通道 = 候选事件 → 校验 → 结算 append |

**结论**：46 个视图的清单不需要增删，但每个视图的定义从"页面上有什么"升级为"查什么事件、能发什么事件"。视图提取的交付物至此完整：**视图清单（是什么）+ 切法归类（怎么切）+ 事件映射（数据从哪来、往哪去）**。

### 4.5 构建链：先有视图，再有属性（v3 增补）

**方向感：设计时反向，运行时正向。**

```
设计时（需求反推）：
  视图定义（谁、为了什么决策）
    → 属性需求（要显示哪些字段）
    → 事件载荷需求（事件必须携带什么）
    → 采集需求（现场要布什么传感器 / 扫码点）

运行时（数据正向）：
  事件 → 提取规则（fold，以属性为单位）→ 本体聚合属性集（聚合不互斥）→ 视图按定义选择属性 → 渲染
```

**纪律一：属性共享，视图只选不提。**
本体 = 唯一 id（句柄）+ k-v 属性聚合，**没有类**。属性的"可能性全集"由写侧定义（所有事件类型可写入的键的并集 = 可能存在什么属性），"物化必要集"由读侧定义（全部视图的需求并集 = 值得固化什么）。一个本体的当前属性集就是它的事件史 fold 出的 k-v 集合，没有类型声明、没有继承。**聚合不互斥：一个属性可属于多个本体**；部分-整体组合是聚合集的包含关系，fold 以属性为单位——写入一次，所有包含该属性的本体观察面同时就位。任何视图不得私自从事件提取属性——否则同一台设备的"当前状态"会在两个视图里算出两个值。推论：未被任何视图需要的属性不物化，留在事件树里按需回放计算（惰性）。

**纪律二：规则一份定义，两处消费，按属性匹配。**
规则不挂在任何"类"上——类不存在。**规则 = 属性谓词 + 处理逻辑**：规则声明自己需要处理哪些属性；一个本体只要聚合了这些属性，规则即可处理它（按属性存在性匹配，非按类型归属）。"车辆""设备"等概念是属性集合的涌现形态，不是先验类型。演化因此是免费的：给本体追加新属性（新事件写入新 k-v），它自动进入所有匹配该属性的规则的射程，无需改 schema、无需迁移。规则定义仅一处，两个消费者：

| 消费者 | 位置 | 用法 |
|---|---|---|
| 写侧 | 软逻辑流水线·规则步 | 过滤候选事件：非法候选不能结算 |
| 读侧 | 视图构建 | 行过滤、列可见性、按钮可用性 |

视图**只消费规则步**（合法性过滤），不消费价值步与意图步——argmax 与承诺窗口是决策的事，不是渲染的事。

**架构性质**：界面上能点的操作，与系统能结算的事件，数学上一致。"按钮灰了但 API 能调通"或"按钮亮着但点了报错"在结构上不可能出现——传统 MES 这两种 bug 的根源正是读侧渲染逻辑与写侧校验逻辑各写一份。

**对本案例的回改**：A3 五状态队列的按钮可用性、F13 锁定车辆的"下线"按钮、F15 报警升级规则——全部由同一份规则定义同时驱动渲染与结算。每个视图的契约最终形态为四元组：

```
View = ( queries        // 查询哪些事件类型 + 折叠规则
       , selects        // 从本体选择哪些属性键（k 的集合）
       , rules          // 对本体的 k-v 求值属性谓词所匹配到的规则（决定行/列/按钮）
       , emits )        // 可发起哪些事件类型
```

### 4.6 存在论分层（v5 增补）

**本体、规则、视图分属两个论域，不可通约：**

| 层 | 成员 | 判据 |
|---|---|---|
| **存在层** | 本体（存在的"体"）、事件（存在的"变"） | 现实中有孪生体，可被多方面观察；删除它，现实事物仍在，但系统失去其句柄 |
| **抽象层** | 规则、视图 | 无现实孪生体；删除它，车间不受任何影响 |

**本体的存在性锚点**：id 不是普通标识符，是**现实事物的数字句柄**——指向车间里那台真实的设备、那辆真实的车。k-v 属性是这个存在的可观察面，不是本体本身。本体不是逻辑游戏，是描述真实存在的现实的。

**规则与视图：形似而本质不同。**

| | 规则 | 视图 |
|---|---|---|
| 范畴 | 规范性（什么是允许的） | 认识性（看到了什么） |
| 观察者 | 无——对所有满足属性谓词的本体一视同仁，普遍适用 | 必有——观察者相对，同一本体千人千面 |
| 与世界的关系 | 从上往下约束可能性空间 | 从可能性空间取一个截面 |
| 消费方向 | 写侧（过滤候选事件） | 读侧（投影属性集） |

规则是"法"，视图是"看"：法不因谁看而改变；看永远不改变世界本身。

**分类检验（任何概念进系统前问两问）**：

1. 它在现实中有孪生体吗？——可被多方面观察的存在 → 本体；没有 → 抽象构造
2. 删掉它，世界变不变？——视图删了世界不变（无人看而已）；规则删了行为变（约束消失）；本体句柄删了，现实事物还在，系统失明

**边界判定**：工单、拉动单、检验计划**是本体**——其现实孪生体是"一项已被承诺的任务"，被计划员、班组长、操作工、ERP 多方观察，其后果真实发生在车间。报表模板、权限配置**不是本体**——纯抽象构造。判据不是"物理实体"，而是"可被多方观察、行为后果真实发生的存在"。

**羊皮纸测试（前数字化载体回溯检验）**：
问"一百年前它是什么？"——有具体载体（这张单、这枚章）→ 存在层；只有普遍陈述（制度条文）或易擦写呈现（黑板）→ 抽象层。区分点在**具体与普遍**：工单是契约，羊皮上写的是"这一批活、这一辆车"，绑定具体存在物；规程书上写的是"所有这类"，不绑定具体。**载体不是判据，绑定具体存在才是判据。**

前数字化时代的四层原型对照：

| 层 | 数字形态 | 羊皮纸时代原型 |
|---|---|---|
| 本体 | id + k-v | 实物本身 + 契约文书（工单、检验卡、拉动单） |
| 事件 | append-only 事件树 | 纸上的章与签字：报工即盖章，落章即事实 |
| 修正事件 | 冲正 / 复核事件 | 会计红字冲销：不刮旧账，红字写新账 |
| 规则 | 属性谓词 + 处理逻辑 | 制度汇编、工艺规程（普遍陈述） |
| 视图 | 四元组渲染 | 车间黑板、产量看板（可擦写、可重画，擦掉不算篡改历史） |

推论：**事实终局不是计算机科学的发明，是账房纪律的再发现**——"落章不可刮、冲正用红字"与 append-only + 修正事件同构。数字化的本质不是发明新东西，而是给四种早已存在的东西换载体，并第一次让它们机器可读、可审计。本案例的现成例证：F8 电子随车卡——纸质随车卡是旧载体，电子卡是新句柄，"扫描纸质卡自动回填档案"（P45）即载体迁移双轨期。

### 4.7 属性多属对 46 个视图的再审视（v7 增补）

"一个属性可属于多个本体"（耳朵⊂脑袋⊂人）落地到本案例，对视图设计有三处实质影响。**46 个视图的清单第三次确认无需增删，但三个类别的内部机制被改写：**

**（1）建模/层级类视图（F5、I1）：从"树编辑器"变为"聚合集声明界面"。**
传统 MES 需要独立维护工厂层级树（车间→工段→班组→设备），西门子的"动态图形建模"卖点亦然。新模型里这棵树不存在——存在的是：注册各粒度本体（车间、区域、工位各有 id），声明各自聚合集的包含关系。F5 定义"走廊、物流通道、区域、工艺工位"，I1 表达"车间、工段、班组、设备"，本质都是**声明哪些属性被哪个本体聚合**。层级是聚合集包含的呈现，不是独立的 schema 硬结构。

**（2）上卷类视图（D1、D2、E2–E7、F16、A6，共 11 个）：机制从"汇总计算"变为"多属就位 + 规则推导"。**
工位完成一件，该属性变化同时在工位、产线、车间三个本体的观察面就位——不需要夜间批处理、不需要 join。整体层的聚合量（车间总产量、产线 OEE）由规则从共享属性推导，产物仍是普通属性，仍可被更上层本体聚合。D2 的"计划产量/实际产量/首次合格率"在同屏并列，是因为这三个属性恰好都被车间本体聚合——口径一致性由此在结构上保证，而非靠报表开发时的人为对齐。

**（3）跨本体视图的自由写明：selects 可跨本体、跨粒度取键，不需要 join。**
- A4 工位作业指导 = 工位本体的属性（工艺信息、物料需求）+ 车辆本体的属性（VIN、配置）同屏——两个本体的聚合集恰好在工位相遇，视图各取所需；
- C1 车辆实时位置总览 = 区域本体聚合了车辆的过点属性，"区域内有哪些车"是区域本体的观察面，不是反查车辆表；
- F14 追溯 = 沿 `corrects`、`binds` 等普通键游走，关系即属性。

**对四元组的影响**：`selects` 的取值域从"单本体的键"扩为"任意本体聚合集中的键"；`rules` 天然跨粒度匹配。视图的粒度自此是**选择的结果**，而非数据结构的前置约束。
