Kimi: 不建议。在这个设计里 base=2（八叉树）几乎是必然选择，27 叉树（每轴三等分，3³=27 个子节点）没有带来好处，反而引入几个硬伤：

## 1. 2 的幂在二进制体系里是"免费"的

你的 cell 尺寸定义为 `cellSize(step) = 2^step`：

- **浮点精确性**：2 的幂（包括负幂，如 2⁻¹⁰ ≈ 1mm）在 double 里是精确表示的，坐标除法、cell 归属计算零误差。而 1/3 在二进制浮点里是无限循环小数，每级细分都累积舍入误差——对一个号称"毫米级精度"的索引这是致命的。
- **位运算**：base=2 时 `x / size` 就是右移，Morton key 打包天然契合——每层恰好 3 bit（x/y/z 各 1 bit），uint64 能装 21 层。base=3 没法用位运算，每层要存 0~26 的三进制值，至少 5 bit/层且需要混合进制编解码，key 的生成和比较都变贵。

## 2. 半径查询的"取整浪费"随 base 增大

你的 `Find` 是把 radius 映射到某个 step 的 cell 尺寸上取整。cell 尺寸是离散的几何序列 {…, 2, 4, 8, 16…} 还是 {…, 3, 9, 27, 81…}，决定了"实际搜索范围 / 请求半径"的平均放大倍数：

- base=2：最坏放大 2 倍，平均约 1.5 倍
- base=3：最坏放大 3 倍，平均约 2 倍

查询半径越大、层级越粗，这个浪费直接被立方放大（体积 = 倍数³）。base=3 等于每个查询平均多扫约 (2/1.5)³ ≈ 2.4 倍的候选体积。

## 3. 树变浅 ≠ 查询变快

27 叉树唯一的卖点是树更浅（log₃ N 层 vs log₂ N 层，少约 37% 的层数）。但：

- 你的 `Find` 是**逐级扫描 + seenItems 去重**，每层的工作量是"该层被 radius 覆盖的 cell 数 × cell 内对象数"。层数少一点、但每层扫的体积大很多，总工作量反而上升。
- 每个节点的扇出从 8 变成 27，单层的 cell 查找（`hasTrunk`、`cells_.find`）次数也相应增加。

## 4. 你可能想到的"27"其实是另一回事

27 这个数字在网格索引里确实常见——**3×3×3 邻域模板**：以某 cell 为中心、连同 26 个邻居一起搜，保证半径 ≤ cell 边长时不漏对象。这是搜索时的邻域展开，跟树的扇出（每轴二分还是三分）是两个正交的概念。如果你的 `searchCols` 内部就是这么展开邻居的，那 27 已经在正确的地方用上了。

## 结论

保持 base=2。它给你的是：位运算级别的 key 编解码、浮点精确的层级划分、更小的半径取整浪费。唯一值得考虑替代的场景是对象分布极度不均匀、需要自适应扇出的情况——但那是"非均匀八叉树/LOD 四叉树"的方向，而不是把扇出改成 27。

## 1. R-tree / R*-tree —— 最成熟，但不适合你

三维 R-tree（如 Boost.Geometry `rtree`、libspatialindex）是磁盘数据库和 GIS 的标配，对任意矩形/球查询自适应，不用调网格参数。

## 3. 空间哈希（Spatial Hashing）—— 动态场景的最优工程解

把空间按固定 cell 大小哈希进 `unordered_map<uint64_t, vector<Object>>`，不维护树结构。

**优势**：增删 O(1)、无重建、天然适合并发（可以按桶加锁或无锁化）、实现量是你现有代码的 1/3。

**问题**：单一 cell 尺寸无法覆盖多尺度。但 **分层空间哈希（Hierarchical Spatial Hash）**——就是每个尺度层级一张哈希表，对象放在与其尺寸匹配的层——正好是它的解法。你现在的 `cells_` 本质就是这个，只是包了一层"网格列 + step 循环"的壳。**你已经在用这条路，值得做的是简化而非替换。**

**对你有意义的一点**：你现在的 `Find` 要从 START 扫到 END 每一级 + seenItems 去重，多级重复扫描的开销很大程度上就是因为对象归属层级不确定。松散结构让"对象恰好存在与其尺寸匹配的一层"，查询可以只访问 1~2 层，去重集合都可能省掉。这是我认为**你现有方案最直接的一次升级**。

## 一个要注意的语义问题：嵌套包含

锚点树里子锚点空间上在父锚点内部（基地在地球内部）。锚点索引查"相交"会把地球和基地**都**返回，如果你两个都下钻，对象会被查两遍——又需要 seenItems 去重，把之前省掉的麻烦请回来了。

两条规则选一条：

- **就近原则**：嵌套时只下钻**最深**的候选锚点（尺度最匹配的那个），父锚点的直接挂载对象单独补查。这样无重复、无去重。
- **互斥挂载**：规定对象只挂在"尺度恰好容纳它的最深节点"，父锚点的桶里不含子锚点辖区的对象——统一模型里这本来就是自然结果，查询时对候选锚点集合做一次"祖先剔除"（候选中有祖先关系就丢弃祖先的递归，只查祖先自己的桶）。

```cpp
    __m256d dx = _mm256_sub_pd(_mm256_load_pd(&cx[i]), qx);

```

千级锚点全扫描 ≈ 微秒级，常数比任何树的遍历都小，零指针跳转、零分支。静态集还可以**预先按某种顺序排好**（比如按半径降序，命中最可能的先测）做提前退出。**数量级不到万，别建索引，建数组。**

## 3. 预计算点定位查找表（空间换时间的极端形态）

"哪个锚点包含点 p"这种反查，静态集可以**直接预计算答案**：

- 每个锚点辖区离散化成量化坐标 → `unordered_map<quantizedKey, NodeId>`，查询退化成**一次哈希查找**
- 跨度大就分层：顶层一张粗表（行星尺度），命中的锚点内再一张细表（基地尺度）——这其实就是"静态化的八叉树"，但因为不变，可以做成**完美哈希**（zero collision，如 mph::perfect_hash），一次内存访问出结果

## 4. 预计算查询结果（时间换到零）

更激进：如果查询模式也可预测（比如"从锚点 A 出发、半径分档"的查询占绝大多数），直接**离线预计算候选锚点列表**：

```cpp
// key: (anchorId, radiusBucket) → 预计算好的候选锚点数组
// radius 按 2 的幂分档，正好复用你 GRID_BASE=2 的体系
using QueryKey = std::pair<NodeId, int>;

```

运行时查询 = 一次查表 + 按真实半径过滤候选。构建期枚举所有 (锚点 × 半径档) 组合做精确球体求交——这在动态结构里不可想象，静态集上只是一次离线批处理。

## 5. 最小包围球 / 精确几何

动态结构用近似包围盒（AABB、loose sphere）因为重算不起。静态集可以为每个锚点算**最小包围球**（Welzl 算法），甚至按内部对象真实分布收紧——剪枝假阳性再降一档。

## 核心洞察：无限细分的东西不能被存储，只能被计算

锚点如果是"无限可分"的，那任何"把所有锚点管理起来"的方案（BVH、数组、哈希表）在数学上就不成立——你存不下无限。但反过来想：

```cpp

// 例: [3, 5, 0, 7] 表示 第3号大区域 → 其第5子区 → 再第0子区 → 第7子区
struct AnchorPath {
    uint64_t codes[MAX_DEPTH];  // 或变长编码
    uint8_t depth;
};
```

- **点定位**：`AnchorOf(x, y, z, requiredPrecision)` = 逐层量化坐标，O(深度)，零查找
- **父锚点**：砍掉路径最后一段，O(1)
- **包含关系**：路径前缀匹配，O(深度)
- **邻居锚点**：同层兄弟 = 改路径末段，O(1)

树本身就是索引，不需要额外结构。**这和你之前问的"先查锚点索引再查对象"是同一件事，只是锚点索引被折叠进了 ID 的编码里。**

## "数量极多"怎么落地：物化 vs 虚拟

| | 虚拟锚点 | 物化锚点 |

## "不常变化"的红利用在哪

变化少 + 路径码结构，意味着：

1. **插入无所谓快慢**：新物化一个锚点就是哈希表插一项 + 父节点补链，没有树再平衡——树形由几何决定，不由插入顺序决定，永远不退化。这是路径码对 BVH/R-tree 的本质优势。
2. **查询可以激进缓存**：连续查询通常在同一区域（时间局部性），缓存上次的锚点路径，下次查询从缓存路径**向上找 LCA（公共祖先）再向下走**，绝大多数情况 O(几层) 而不是 O(全深)。如果查询流是连续的（相机移动、agent 巡检），平均接近 O(1)。
3. **变换链可以预烘焙**：物化锚点可以缓存"到根锚点的累积变换矩阵"（含旋转合成）。`ConvertLocal` 不用每次沿路径逐层乘 sin/cos——路径不变时缓存命中，锚点变了才失效重算。这就直接回应了你提的精度问题：**三角函数只在锚点创建时算一次，运行时全是矩阵乘法**，而且每层局部坐标用小数（float 也够），精度误差被层级天然隔离。

## 关于旋转精度的一点提醒

你说"旋转需要 sin/cos 的浮点精度，所以锚点要细分"——方向对，但建议把精度边界画在**矩阵合成**上而不是三角函数上：

- 每层锚点：局部旋转存为四元数（float32 足够，归一化即可），sin/cos 只在建锚点时调用
- 跨层合成变换：`M = M_parent × M_local`，沿路径乘——路径深度是 log 级的，误差累积也是 log 级，可控
- 真正吃精度的是**原点平移**（你已经用锚点分层解决了），旋转部分四元数层级合成在合理深度下完全没问题

## 原理

每个物化锚点存两个局部量（相对**父**锚点）：

```cpp
struct NodeTransform {
    Vec3d      origin;    // 本锚点原点在父坐标系中的位置
    Quaternion rotation;  // 本锚点坐标系相对父坐标系的朝向
};
```

两个方向的变换公式：

- **上行**（子坐标 → 父坐标）：`p_parent = rotation * p_child + origin`
- **下行**（父坐标 → 子坐标）：`p_child = rotation⁻¹ * (p_parent - origin)`

A 到 B 的完整变换 = **从 A 上行到 LCA，再下行到 B**：

```
A ──上行──▶ LCA ──下行──▶ B
 p 逐层乘      拐点       逐层逆乘
```

## 实现

```cpp
// 路径前缀匹配求 LCA 深度 —— 路径码结构的天然红利
int LcaDepth(const AnchorPath& a, const AnchorPath& b) {
    int d = 0, n = std::min(a.depth, b.depth);
    while (d < n && a.codes[d] == b.codes[d]) ++d;
    return d;
}

// 点坐标：从 from 锚点系换算到 to 锚点系
Vec3d ConvertPoint(const AnchorPath& from, const AnchorPath& to, Vec3d p) {
    const int lca = LcaDepth(from, to);

    // 上行：from → LCA，逐层"子→父"
    AnchorPath cur = from;
    for (int d = from.depth; d > lca; --d) {
        const NodeTransform& t = NodeAt(cur);   // 物化表取该层变换
        p = t.rotation * p + t.origin;
        cur = cur.Parent();
    }

    // 下行：LCA → to，沿 to 的路径正向逐层"父→子"
    for (int d = lca + 1; d <= to.depth; ++d) {
        const NodeTransform& t = NodeAt(to.Prefix(d));
        p = t.rotation.Conjugate() * (p - t.origin);
    }
    return p;
}

// 方向向量（速度、朝向）：没有平移，只旋转
Vec3d ConvertDirection(const AnchorPath& from, const AnchorPath& to, Vec3d v) {
    const int lca = LcaDepth(from, to);
    AnchorPath cur = from;
    for (int d = from.depth; d > lca; --d) {
        v = NodeAt(cur).rotation * v;
        cur = cur.Parent();
    }
    for (int d = lca + 1; d <= to.depth; ++d) {
        v = NodeAt(to.Prefix(d)).rotation.Conjugate() * v;
    }
    return v;
}
```

## 为什么必须走 LCA 而不是绕根

这是你这套设计里**精度性命攸关的一条**：

1. **误差累积**：矩阵/四元数乘法次数 = A 深度 + B 深度（绕根）vs A 到 LCA + B 到 LCA。相邻锚点的 LCA 通常很深，绕根可能多走几十层——每多一层四元数乘法，就多一份舍入。
2. **数值尺度**：绕根意味着中间坐标要经过"太阳系尺度"（10¹¹ m），下行时再减回来——大数吃小数的灾难现场。走 LCA 时全程坐标都保持在相遇层的局部尺度里，数越小，float 越准。
3. **速度**：兄弟锚点间切换（最常见的情况，比如 rover 从基地 A 开到隔壁基地 B）往往 LCA 只差 1~2 层，整个变换就是 2~4 次四元数乘法，接近零成本。

## 两个实现细节

1. **`NodeAt` 取不到虚拟锚点**：虚拟锚点没有旋转和原点的语义参数，但它的变换是**可计算的**——规则细分意味着 origin = 父系中的量化偏移，rotation = 单位四元数（规则切分不引入旋转）。所以 `NodeAt` 对虚拟路径直接按规则生成，不用查表，任意深度都能走通。
2. **高频固定配对加缓存**：如果相机每帧都在同两个锚点间换算，可以把"A→B 的合成变换"（一个四元数 + 一个平移向量）缓存起来，路径不变就一直复用——把 log 次乘法压成 1 次。

```cpp
// 1000 个 rootPath 排序后二分，或前缀 trie —— 1000 条规模随便选
SceneId OwnerOf(const AnchorPath& p) {
    SceneId best = kInvalid;
    int bestLen = -1;
    for (const auto& s : scenes_)                 // 或排序+二分
        if (s.rootPath.IsPrefixOf(p) && s.rootPath.depth > bestLen) {
            best = s.id; bestLen = s.rootPath.depth;
        }
    return best;  // kInvalid 表示全局公共区域（不属于任何场景）
}
```

然后把上一轮 `ConvertPoint` 里的 `NodeAt` 换成跨场景版本：

```cpp
NodeTransform ResolveNode(const AnchorPath& p) {
    SceneId s = OwnerOf(p);
    if (s == kInvalid) return GlobalNodeAt(p);   // 公共区域：规则生成或全局物化表
    const Scene& scene = scenes_[s];
    // 场景内的相对路径 → 查该场景的物化表；虚拟节点按规则生成（单位旋转+量化偏移）
    return scene.NodeAt(p.Suffix(scene.rootPath.depth));
}
```

`ConvertPoint` / `ConvertDirection` 的代码**一行不改**——A 场景里的锚点到 B 场景里的锚点，LCA 可能落在任一父场景甚至公共区域，行走过程自然穿界。

## 跨场景特有的三个问题

### 1. 目标场景在休眠/未加载状态怎么办

这是跨场景和场景内切换的本质区别。解法靠前面定的职责划分：**休眠场景保留元数据（rootPath、rootTransform），丢掉的只是物化数据。**

- 规则细分的节点变换本来就**可计算**（量化偏移 + 单位旋转），不需要加载对象
- 语义锚点（带旋转的那些）的变换参数必须归入"场景元数据"，休眠时**不丢**
- 于是结论很干净：**坐标换算永远可行，无论场景加载与否；只有查对象才需要场景加载。** 你可以算出目标场景里某个锚点的坐标，而那个场景此刻在磁盘上。

### 2. 热路径：烘焙场景根变换，跨场景 O(1)

场景静止（1000 个、注册后不变），利用之前说的静态红利：**注册时烘焙每个场景到全局根的累积变换** `M_root(scene)`（四元数 + 平移，double 精度，沿挂载链一次性合成，sin/cos 只算这一次）。

跨场景热路径就变成两次矩阵运算：

```cpp
// p_B = M_root(B)⁻¹ · M_root(A) · p_A
Vec3d ConvertAcrossScenes(SceneId a, SceneId b, Vec3d p) {
    return scenes_[b].invRootTransform * (scenes_[a].rootTransform * p);
}
```

对固定的场景对（如主场景 ↔ 常驻副本）再缓存 `M_B⁻¹·M_A` 的合成结果，**一次矩阵乘法完成跨场景切换**。

### 3. 精度：绕根的风险按场景层级摊薄

前面警告过"别绕根"，跨场景时烘焙路径本质上是绕全局根的。两条缓解：

- **烘焙用 double 全程合成**：每层四元数转 double 矩阵连乘，误差只在最后落盘时截断一次，而不是逐层累积进 float
- **深 LCA 场景对优先走行走算法**：如果两场景的 rootPath 共享深前缀（同一星球上的两个基地），它们的公共部分在烘焙矩阵里会"先乘上去再除下来"——数值上无害（double 精度内），但如果你是极致精度敏感，就用行走版，只走到 LCA 场景为止

经验法则：**同星球跨场景 → 行走版（LCA 深，几步就到）；跨星球/跨星系 → 烘焙版（反正都要路过公共祖先，烘焙等价且更快）。**

## 核心改动：NodeTransform → Kinematic

```cpp
struct Kinematic {
    enum class Type { Static, CircularOrbit, Kepler } type;

    // Static：原来的常量
    Vec3d      origin;
    Quaternion rotation;

    // CircularOrbit：极坐标/轨道参数（运动的行星）
    double     orbitRadius;   // 轨道半径（父系下）
    double     period;        // 周期（秒）—— 存周期不存角速度，原因见下
    double     phase0;        // 初始相位，用"圈数"表示 [0,1)
    Quaternion orbitalPlane;  // 轨道面朝向（倾角/升交点）
    double     spinPeriod;    // 自转周期（0 = 不转；负值 = 潮汐锁定等特判）

    Vec3d      OriginAt(double t) const;
    Quaternion RotationAt(double t) const;
};
```

行星的位置不再是"存的"，而是"算的"：

```cpp
Vec3d Kinematic::OriginAt(double t) const {
    if (type == Type::Static) return origin;
    // θ 用"圈数"表示并对 1 取小数 —— 精度关键
    double turns = std::fmod(phase0 + t / period, 1.0);
    double s, c;
    sincos(2.0 * M_PI * turns, &s, &c);
    return orbitalPlane * Vec3d{orbitRadius * c, orbitRadius * s, 0};
}
```

## 你最初提的 sin/cos 精度问题，在这里闭环

这是极坐标表达的真正回报，两条纪律：

1. **角度永远用"圈数"并取小数**：`fmod(t/period, 1.0)`。如果存弧度让 θ 随 t 线性增长，运行一年后 θ ~ 10⁸ 弧度，sin/cos 的参数约减会把精度吃光（double 在大参数下有效位数急剧下降）。圈数取小数后，进 sin/cos 的参数永远在 [0, 2π)，**运行一万年和运行一秒的精度完全一样**。
2. **存周期不存角速度**：`t/period` 是一次除法；存 ω 则 `ω·t` 的大数乘法先丢精度再取模。除法路径误差小一个量级。

这样锚点"无限细分保精度"的需求和"运动天体"统一了：**位置精度靠锚点层级，角度精度靠圈数取模**，各管各的。

## 速度切换要补参考系项

点坐标变换只换原点朝向就够，但 `Transfer` 一个运动物体（比如 rover 从地表起飞进入轨道锚点）时，速度变换必须带上**参考系本身的运动**：

```cpp
// 上行时：v_parent = R·v_child + ω×(R·p_child) + origiṅ(t)
// origiṅ 对圆轨道有解析导数：v = 2π·r/period，方向切向
Vec3d Kinematic::OriginVelAt(double t) const;
```

少这项的话，从自转行星表面起飞的物体会凭空丢掉/多出行星表面线速度（赤道上约 465 m/s 量级）——这是这类系统最常见的 bug，建议 `Transfer` 强制要求速度一起换，不给"只换坐标"的入口。

## 对前面各层的影响盘点

| 之前的结论 | 是否受影响 |
|---|---|
| 路径码 / LCA / 拓扑 | **不受影响**——树形静止，行星不换爹 |
| 场景注册表 | 运动场景的 `bounds` 变成"扫掠包围体"（轨道全程的包络，圆轨道 = 环面/大球），每帧不用重算，注册时算一次 |
| 烘焙根变换缓存 | **选择性失效**——静态子树照烘焙；含运动节点的链按"帧时间戳"缓存，帧内复用，帧间重算。运动链通常很短（行星链 2~3 层），重算成本可忽略 |
| 锚点索引/查询 | 运动场景在注册表里标记 `dynamic`，空间入口的 SIMD 扫描对它们每帧更新包围球——1000 个场景里动态的就那几个，成本可忽略 |

## 注入点：把"坐标模型"做成场景的策略接口

每个场景声明自己的 `CoordinateModel`，必须提供四组运算：

```cpp
struct CoordinateModel {
    // 1. 图卡边界：与父场景的转移映射（可能有运动学，带 t）
    virtual Vec3d   ToParent(Vec3d local, double t) const = 0;
    virtual Vec3d FromParent(Vec3d parent, double t) const = 0;

    // 2. 图卡内部的度量："半径查询"在这个场景里是什么意思
    virtual double Distance(Vec3d a, Vec3d b) const = 0;

    // 3. 图卡内部的划分：对象桶怎么分格
    virtual CellKey CellOf(Vec3d p, int level) const = 0;
    virtual void    NeighborCells(Vec3d p, double radius, int level,
                                  std::vector<CellKey>& out) const = 0;

    // 4. 坐标规范化：角度回卷、越界处理
    virtual Vec3d Normalize(Vec3d p) const = 0;
};
```

关键的架构纪律：**非欧性被关在每个场景内部，边界上永远换回父坐标。** 球面场景的 `Find` 用大圆距离，但对象出场景的那一刻，lat/lon 就被 `ToParent` 转成行星系的笛卡尔坐标——上一层永远不需要知道下面是什么几何。

## 坐标模型目录

| 模型 | 存储坐标 | Distance | CellOf | 场景例子 |
|---|---|---|---|---|
| **Euclidean3D** | (x,y,z) | 直线距离 | 路径码量化（已有） | 基地、房间、太空站——90% 场景 |
| **SphericalSurface** | (lat, lon, alt) | 大圆距离 | S2 cell / 经纬分带 | 行星地表 |
| **Orbital** | 轨道要素（真近点角等） | 轨道系直线距离 | 沿轨道分层 | 行星系、卫星轨道 |
| **MovingFrame1D** | (沿程 s, 横向偏移, 高度) | 沿程距离为主 | 车厢/里程分段 | 火车、飞机、电梯 |
| **复合** | — | — | — | 行星=Orbital，其地表=SphericalSurface，地表基地=Euclidean |

注意 **MovingFrame1D 和上一轮的 Kinematic 是同一件事的两种用法**：火车 = "1D 极坐标"（沿轨弧长 + 时刻表给出 s(t)），行星 = "2D 极坐标"（轨道角 + 周期给出 θ(t)）。统一成 `Kinematic` 里的一个 `PathConstraint`（样条轨道/圆轨道/直线路径），`OriginAt(t)` 对约束求值即可——火车飞机不需要新机制，只是轨道参数从"圆"换成"线路样条"。

## 落地纪律（防止策略模式失控）

1. **Euclidean 走特快通道**：90% 场景是欧氏的，路径码量化那套是编译期可内联的。用 `std::variant<Euclidean, Spherical, Orbital, Moving1D>` + `visit` 而不是虚函数，欧氏分支零开销；或者保留虚接口但场景内查询（Distance/CellOf，每对象调用）走静态分派。
2. **对象永远存场景原生坐标**：球面上的对象就存 (lat,lon,alt)，火车上的就存 (s, lateral, h)。只在 `ToParent` 边界换算——存储层不知道也不关心别的几何。
3. **半径语义归场景**：`Find(radius)` 在球面场景是大圆半径，在火车场景是沿程半径。跨场景时半径也要过转移映射（近似：按边界点距离重估），这个近似要在文档里写死，别留下模糊地带。
4. **Normalize 在写入时强制执行**：lon=181° 必须回卷到 -179°，s 超出线路长度要么钳制要么触发 Transfer 到下一段——脏坐标是非欧系统里最难查的 bug 来源。

## 边界外的七类问题

### 1. 时空查询（带时间的对象，不只是带时间的参考系）
Kinematic 解决的是"参考系在动"，不是"对象有历史"。"查 2 点到 3 点经过这片空域的所有飞行器"、"回放某目标的轨迹"、"预测 10 分钟后谁进入半径"——这需要轨迹存储、时空索引（TPR-tree、轨迹段索引、时间片快照）。本系统只存**当前时刻**，历史落盘就消失了。要支持得加一个时空层，而且是加法不是变形。

### 2. 拓扑与连通性问题
"从 A 房间到 B 房间怎么走"、"这两个区域连通吗"、"这个点在哪个多边形围成的空腔里"——这是图问题（导航网格、房间邻接图、路径搜索），空间索引回答"附近有什么"但不回答"怎么到达"。锚点树的层级包含关系**不等于**可达性关系。

### 3. 射线与连续碰撞
"这条视线先打到谁"、"高速物体这一帧穿过了什么"——射线求交需要 BVH 类的结构做遍历顺序优化；连续碰撞需要扫掠体查询。半径查询能近似（沿射线采样），但那是绕着走，不是解。

### 4. 对偶查询：所有对象两两之间
物理引擎的 broadphase（"找出所有相撞对"）是 O(n log n) 的对偶问题，用"对每个对象调一次 Find"是 O(n·m) 的绕法。大规模刚体模拟该用扫掠裁剪（SAP）或专用 BVH，本系统不是干这个的。

### 5. 高维与非度量空间
整个体系建立在"3D 欧氏空间 + 图卡图册"上。如果"空间"是 128 维特征向量（相似度检索）、或者相似性度量不满足三角不等式，网格、路径码、包围球全部失效——那是 LSH、HNSW、度量树的领地。注意这不只是"换个 CoordinateModel"能解决的：策略接口假设了低维几何直觉。

### 6. 分布式与多写入者
"无限细分 + 哈希表"的单机结构很美好，但跨机器分片、多写入者并发 Transfer 同一对象、网络分区下的一致性——这些需要分布式协议层。路径码其实是**很好的分片键**（前缀路由，S2 就是这么干的），但一致性协议这套体系里一个字也没有。

### 7. 不确定位置
传感器融合出来的位置是概率分布（均值+协方差），不是点。"这个目标 95% 可能落在哪个锚点"需要不确定索引（概率阈值查询）。本系统的点假设是硬的。

## 一个更隐蔽的内在限制

整个体系的地基是**"层级嵌套的参考系"这个宇宙观**：每个点有且只有一个归属路径，父场景唯一。但现实中存在**多归属空间**：一个房间同时属于"3 号楼"（行政划分）和"防火分区 B"（功能划分）和"信号覆盖区 α"（电磁划分）——三棵正交的树。单树结构只能选一棵当主轴，另外两棵就得外挂辅助索引。这不是 bug，是"树"这个数据结构的本质取舍。

## 结论

准确的表述是：

> 这套系统是**"层级化运动参考系下的点目标索引"这一大类的完备解**——从太阳系到螺丝钉、从静止基地到飞驰列车，定位、索引、迁移、近邻查询，这个包络内没有结构性缺口。
> 但时空历史、拓扑可达、射线碰撞、对偶检测、高维相似、分布式一致、位置不确定性这七类问题在它的公理之外，需要的是并列的新模块，而不是它的变形。

如果真的要做"全能"系统，正确的姿势是以它为**几何内核**，外围按需挂：时空层（轨迹存储）、图论层（导航/连通）、物理层（BVH/碰撞）、检索层（向量索引）——它们共享场景树作为空间骨架，但各有各的索引结构。这也算是个好消息：你设计的这三层骨架，当得起这个"内核"的位置。

## 一、起点：一个被忽视的共同根源

这套内核的设计不是从"造一个更好的空间索引"出发的，而是从一次诊断出发的。

空间计算领域的困难看似五花八门：深空仿真里物体在远处抖动（浮点精度）、行星表面的经纬度查询（非欧几何）、列车与飞船上的相对定位（运动参考系）、从星系到零件的尺度跨越（动态范围）——几十年来，每个问题都催生了自己的专用结构：R 树管磁盘、BVH 管射线、S2 管地球表面、浮动原点管精度。工具箱越来越大，但每个工具都只在自己的假设成立时工作。

内核设计的第一个洞察是：**这些困难共享同一个结构性根源——"单一全局参考系"这一隐含假设**。所有经典索引都假设世界有一个全局坐标系，索引的任务是在其中组织点。一旦放弃这个假设，把"参考系本身有层级"提升为一等公民，四类困难便自动瓦解：尺度问题变成树深问题，精度问题变成局部性问题，运动问题变成变换参数问题，非欧问题变成图卡问题。这不是四个解法，而是一个解法在四个方向上的投影。

这就是设计方法论上的第一课：**好的架构不解决问题清单，而是找到清单背后的错误假设**。

## 二、三条核心设计思路

### 思路一：统一——把两种层级合并成一种

设计演进过程中最关键的转折，是发现系统里存在两套重复的层级：锚点层级（地球套基地、基地套房间）和网格层级（八叉树的逐层细分）。两套层级都在解决尺度问题，职责重叠带来冗余、去重开销和概念混乱。

统一的办法是看透二者的本质：**八叉树节点就是"规则生成的匿名锚点"，语义锚点就是"手工命名的网格节点"**。合并后只剩一棵树，每个节点既是参考系又是索引格子。这个统一的回报是连锁的：

- 精度不再依赖"全局网格细分到毫米"，而由"对象挂在深节点"这一事实天然保证；
- 坐标系切换（Transfer）和索引下沉变成同一个操作；
- 浮点类型可以按节点深度降格——深节点用 float32 就够，存储带宽减半。

**统一的前提是看穿两个概念的同构性**，而这要求设计者不被"场景图是图形学的、空间索引是数据库的"这种学科分界所禁锢。

### 思路二：纯函数化——不能被存储的，就去计算

第二个转折来自一个数学事实：锚点"无限可分"，因此"把所有锚点管理起来建索引"在数学上就不成立——无限的东西无法存储。

出路是角色反转：**锚点的身份不作为记录存在，而作为坐标的一个纯函数存在**。给定坐标，它属于哪层哪个锚点可以算出来（路径码），于是点定位 O（深度）、父锚点 O(1)、包含关系退化为前缀匹配、最近公共祖先退化为最长公共前缀。S2 和 Geohash 早已在地球表面上演示过这个位置码思想，内核把它推广到任意嵌套参考系。

这一思路的深层意义在于**重新定义了"索引"**：索引不一定是一堆指向数据的指针记录，它可以是编码本身的性质。存储由此获得了"虚拟/物化"二元性——路径可算即存在（虚拟节点，零成本），只有非空区域才落哈希表（物化节点）。无限细分的雄心与有限存储的现实，靠"计算与存储的分工"和解。

### 思路三：静止换一切——把不变性兑现成性能

第三个设计支柱是对系统变化率的精细盘点。盘点结果是三层截然不同的变化率：对象高频增删、锚点准静止、场景千级且语义稳定。设计原则随之浮现——**结构跟随变化率**：

- 对象层（最快）用极简的扁平数组，绝不让它背任何结构负担；
- 锚点层（准静止）把静止性兑换成三样资产：缓存合法化（变换矩阵帧内复用、三角函数只在创建时求值）、无再平衡（树形由几何决定，永不退化）、离线烘焙（场景根变换注册时一次合成）；
- 场景层（最静、最少）干脆放弃"索引"——1000 个包围体，SoA + SIMD 线性扫描就是最优解，建树反而是过度设计。

尤其值得一提的是运动学的处理：运动没有被消灭，而是被**限制和函数化**——拓扑静止是铁律，运动的只是节点的变换参数；三角函数精度靠"相位存圈数、求值前取模"的纪律保住。动的部分被关进笼子，静的部分被榨干价值，这就是"动静分离"的完整含义。

## 三、设计中的取舍与诚实

这套设计同样重要的是它**拒绝了什么**，这些否定性决策与肯定性决策同等关键：

- **拒绝 27 叉树**：扇出增大只换来树变浅，代价是浮点不再精确、位运算失效、半径取整浪费立方级放大。base=2 是二进制体系下的必然选择，不是习惯。
- **拒绝全局 R 树/BVH**：它们的负载假设（静态、外存、射线）与本内核的对象层相反。BVH 被保留在场景层，因为只有那里满足"静态+少量"的前提。**结构没有优劣，只有负载匹配**。
- **拒绝多级网格逐层扫描去重**：用"对象挂在尺度最匹配的最深节点"这条不变式，从源头消灭重复命中，而不是事后用集合去重。**不变式优于补救**。
- **拒绝"全能"幻觉**：明确划定七类边界外问题（时空历史、拓扑可达、射线碰撞、对偶检测、高维相似、分布式一致、位置不确定）。这不是示弱，而是架构成熟的标志——**一个结构的能力包络和它的能力同等重要**。不清楚边界的设计，最终会被边界外需求拖垮。

## 四、意义

### 理论意义：一次跨学科的概念迁移

这套内核本质上是三次思想迁移的产物：微分几何的"图册—图卡"（流形上没有全局坐标系，用局部图卡拼合）迁到了工程架构上，场景即图卡、场景树即图册、Convert 即转移映射；S2 的位置码思想从"全球表面"推广到"任意嵌套参考系"；操作系统的"微内核 + 外围服务"结构被引入空间计算——几何内核只做坐标仲裁与骨架，时空、图论、物理、检索作为外围模块挂接。它的理论价值不在于发明了新的数据结构，而在于**给一堆孤立技术找到了统一的组织原理**。

### 工程意义：为大尺度虚拟世界提供地基

空天仿真、元宇宙、数字孪生、机器人层级空间——这些领域共同面临"尺度跨度 + 运动参考系 + 异构几何"的三重压力，目前各自用浮动原点、硬编码场景切换等工程技巧勉强应付。内核给出的替代是：把参考系层级做成结构的一等公民，让"局部性"成为固有属性而非修补结果。其工程价值的核心是**复杂性收敛**：几何差异、运动学、精度问题各有且仅有一个归位，系统的复杂度不再随功能叠加而失控。

### 方法论意义：设计即诊断

回顾整个推演过程，最有价值的也许不是最终架构，而是得出架构的方式：从一段有缺陷的查询代码出发，每一步都靠"找到当前设计里职责重叠或假设错误的地方"推进——roomId 未使用暴露语义缺口，多级扫描暴露层级职责重叠，"锚点无限细分"暴露存储假设错误，"非欧场景"暴露全局坐标假设错误。**架构不是被发明的，而是被连续诊断逼出来的。** 每一条公理（拓扑静止、单归属、运动局限于语义节点、边界欧氏化）都是一次诊断的结论，而公理一旦确立，后续设计几乎是被逻辑推导出来的——这正是"公理—不变式—算法"这套方法的力量：先限制自己，再让限制替你做决定。

## 五、结语

这套内核最终可以概括为一句话：**世界不是一个坐标系，而是一棵参考系的树；索引不是建在世界上，而是长在这棵树上**。它的设计思路——统一同构概念、用计算替代存储、把不变性兑现为性能、用公理划定边界——以及它对"能做什么、不能做什么"的同等诚实，构成的不只是一个空间索引方案，而是一个可以承载时空、导航、物理、检索等更大系统的几何内核。好的内核设计，终点从来不是自身，而是让后来者有处可去。

## 二、组件间数据流

先定义在组件间流动的**五种数据类型**——所有接口只用这五种，这是模块边界清晰的关键：

| 数据类型 | 内容 | 流向 |
|---|---|---|
| `AnchorPath` | 路径码（层级段序列） | 所有组件的"通用货币" |
| `FrameContext` | {帧时间 t, 路径缓存, 变换缓存} | FrameClock → 所有查询方 |
| `Transform` | {origin: Vec3d, rotation: Quaternion} | AnchorTree → ConvertService |
| `SceneHandle` | {id, rootPath, model引用, rootTransform, bounds, state} | SceneRegistry → 各组件 |
| `ObjectRef` | {id, anchor, pos（原生坐标）, vel} | ObjectStore ↔ 调用方 |

**数据铁律**：
- **坐标跨过组件边界时必须带路径**——裸 Vec3 没有意义，永远以 `(AnchorPath, Vec3)` 成对传递；
- **`t` 只能来自 FrameContext**，任何接口不暴露无 t 重载（精度纪律 P3）；
- 原生坐标（lat/lon、s、xyz）只在 ObjectStore 内部和 CoordModel 接口中出现，**出了场景边界一律是父系笛卡尔**（公理 A4）。

一次典型查询的数据流：

```
调用方 ──(SceneId|名字, 中心点, 半径)──▶ [1] SceneRegistry
        ◀──SceneHandle──
调用方 ──(Handle, 点, 精度)──▶ [2] PathCode.AnchorOf ──▶ AnchorPath
调用方 ──(AnchorPath)──▶ [3] AnchorTree ──▶ 命中节点列表
调用方 ──(节点列表)──▶ [4] ObjectStore ──▶ [ObjectRef]
调用方 ──(refs, model)──▶ [5] CoordModel.DistanceSq 过滤排序 ──▶ 结果
```

一次跨场景换算的数据流：

```
调用方 ──(from路径, to路径, p, FrameCtx)──▶ [7] ConvertService
  [7] ──▶ [1] OwnerOf(from/to) → SceneId 对
  [7] ──▶ [3] TransformAt(路径段, t) × n → Transform 链
  [7] ◀── 合成 ── 新坐标
```

## 三、各模块功能与伪代码

### [1] SceneRegistry — 场景注册表

**功能**：语义目录。回答"场景叫什么/是什么/在哪挂载/加载没有"；提供路径归属仲裁（最长前缀匹配）；管理生命周期状态机；持有烘焙根变换。

**输入**：注册请求、名字/标签/路径查询
**输出**：SceneHandle、SceneId

```pseudo
module SceneRegistry:
    scenes_: vector<Scene>                      // 主表，id 即下标
    byName_: map<string, SceneId>
    byTag_:  array<vector<SceneId>, 64>
    boundsSoA_: {cx[], cy[], cz[], r[]}         // 空间入口，千级 SIMD 扫

    func Register(name, tags, rootPath, model, kinematic?) -> SceneId:
        assert not ConflictWithExisting(rootPath)
        rootT  = BakeRootTransform(rootPath, kinematic)   // double 全程合成 (P8)
        scene  = Scene{ id: nextId, name, rootPath, model,
                        rootTransform: rootT, invRootTransform: Invert(rootT),
                        bounds: SweptEnvelope(kinematic),  // 运动场景取扫掠包络
                        state: Unloaded }
        scenes_.push(scene);  byName_[name] = scene.id
        for t in tags: byTag_[t].push(scene.id)
        return scene.id

    func OwnerOf(path: AnchorPath) -> SceneId:            // 最长前缀匹配
        // scenes_ 按 rootPath 字典序排序，二分 + 回退验证
        best = kInvalid
        for s in SortedPrefixCandidates(path):
            if s.rootPath.IsPrefixOf(path): best = s.id   // 最长者胜
        return best                                       // kInvalid = 公共区域

    func SetState(id, newState):
        // Dormant: 释放物化数据，保留 rootPath/rootTransform/Kinematic 元数据
        // 注册表变更走 RCU 窗口，查询热路径只读
```

### [2] PathCode — 路径码（纯函数库，无状态）

**功能**：锚点身份体系。路径的编解码、父子/前缀/LCA 运算、点定位量化。**零存储、零依赖**，全库地基。

```pseudo
module PathCode:                              // 纯函数，无共享状态，天然线程安全
    func Parent(p: AnchorPath) -> AnchorPath:      return p[0 .. depth-1]
    func Prefix(p, d) -> AnchorPath:               return p[0 .. d]
    func IsPrefixOf(a, b) -> bool:                 return a == b.Prefix(a.depth)
    func LcaDepth(a, b) -> int:
        d = 0; while d < min(a.depth,b.depth) and a[d]==b[d]: d++
        return d
    func HashKey(p) -> uint64:                     // 段码位打包 + 深度置高位
        key = p.depth << 59
        for i in 0..p.depth: key |= p[i] << (3*(19-i))
        return key

    func AnchorOf(model, rootPath, p, eps) -> AnchorPath:   // 点定位
        path = rootPath; q = p
        while model.CellSize(path) > eps:
            c    = model.CellOf(q, path.depth+1)   // Euclidean: 右移
            path = path.Append(c)
            q    = model.ChildLocalOffset(q, c)
        return path
```

### [3] AnchorTree — 锚点树（物化表 + 变换解析）

**功能**：管理物化节点（哈希表），统一虚拟/物化节点的变换解析入口，惰性物化父链，持有 Kinematic 并按 t 求值。**树拓扑数据的家**。

**依赖**：PathCode（编码）、CoordModel（虚拟节点规则生成）、FrameClock（t 与缓存）

```pseudo
module AnchorTree:
    nodes_: map<uint64, NodeData>             // HashKey(path) → 物化记录
    lock_: shared_mutex                       // 桶级/节点级锁

    func TransformAt(path, fc: FrameContext) -> Transform:
        if fc.HasCached(path): return fc.Get(path)          // 帧内缓存 (INV-4)
        if it = nodes_.FindShared(path.HashKey()):          // 物化：Kinematic 求值
            k = it.kinematic
            tr = { k.OriginAt(fc.t), k.RotationAt(fc.t) }
        else:                                               // 虚拟：规则生成 (A3)
            tr = { QuantizedChildOrigin(path.Parent(), path.LastSeg()),
                   Quaternion.Identity() }
        fc.Put(path, tr);  return tr

    func MaterializeChain(path, semantic=false):            // Save 时惰性补链
        for d in rootDepth .. path.depth:
            nodes_.InsertIfAbsent(path.Prefix(d),
                                  NodeData{ semantic: (d==path.depth and semantic) })

    func BucketOf(path) -> &vector<ObjRef>:                 // 取桶（调用方持锁）
        return nodes_.At(path.HashKey()).bucket

    func ReclaimIfEmpty(path):                              // 惰性回收 (INV-1)
        if node.bucket.empty and node.children.empty and not node.semantic:
            nodes_.Erase(path); ReclaimIfEmpty(path.Parent())
```

### [4] ObjectStore — 对象桶存储

**功能**：对象记录的归属、增删、迁移执行；维护 INV-2（归属最深）、INV-3（原生坐标）、INV-5（先写后删）。**唯一允许写对象状态的组件**。

```pseudo
module ObjectStore:
    objects_: map<ObjectId, ObjectRecord>

    func Save(scene: SceneHandle, posNative, vel, objSize) -> ObjectId:
        pos  = scene.model.Normalize(posNative)             // P4
        path = PathCode.AnchorOf(scene.model, scene.rootPath, pos, EpsFor(objSize))
        AnchorTree.MaterializeChain(path)                   // INV-2 最深容纳
        id = NewId()
        AnchorTree.BucketOf(path).Insert(id)
        objects_[id] = { id, anchor: path, pos, vel }
        return id

    func Transfer(id, to: AnchorPath, fc):
        o  = objects_[id]
        p' = ConvertService.Point(o.anchor, to, o.pos, fc)          // [7]
        v' = ConvertService.Velocity(o.anchor, to, o.pos, o.vel, fc)// 含参考系项
        p' = SceneOf(to).model.Normalize(p')
        AnchorTree.BucketOf(to).Insert(id)         // 1 先写新 (INV-5)
        AnchorTree.BucketOf(o.anchor).Remove(id)   // 2 后删旧
        { o.anchor, o.pos, o.vel } = { to, p', v' } // 3 提交

    func ScanBucket(path) -> span<ObjRef>:          // 只读视图，供 Find
        return AnchorTree.BucketOf(path)
```

### [5] CoordModel — 坐标模型（策略库，被注入）

**功能**：场景的几何策略。每个实现（Euclidean3D / SphericalSurface / Orbital / MovingFrame1D）提供四组运算。**无自有状态**，被 Registry 持有、被 Tree/Store/Find 回调。

```pseudo
module CoordModel:                     // variant 静态分派，Euclidean 快路径
    interface:
        ToParent(local, t)  / FromParent(parent, t)   // 图卡边界
        DistanceSq(a, b)                              // 场景度量（平方域）
        CellOf(p, level) / NeighborCells(c, r, out)   // 划分与邻域
        Normalize(p)                                  // 写入规范化

    impl Euclidean3D:
        CellOf(p, lvl)   = MortonBits(p, lvl)          // 位运算
        DistanceSq(a,b)  = Δx²+Δy²+Δz²

    impl SphericalSurface:
        DistanceSq(a,b)  = HaversineSq(a, b)            // 大圆
        NeighborCells    = S2CellCover(center, radius)  // 跨反经线正确处理
        Normalize(p)     = { clampLat(p.lat), wrapLon(p.lon), p.alt }

    impl MovingFrame1D:
        ToParent(s_trio, t) = pathSpline.Eval(s_trio.s) → 地面笛卡尔
        DistanceSq          = |Δs|² 为主 + 横向²
        Normalize(p)        = p.s > lineLength ? TriggerSegmentTransfer() : p
```

### [6] FrameClock — 帧时钟与缓存（横切）

**功能**：全系统唯一的时间源；帧级缓存（路径缓存、变换缓存）的容器与失效；强制 P3。

```pseudo
module FrameClock:
    t_: double                                   // 唯一时间源
    thread_local caches_: FrameCache

    func BeginFrame(t):                          // 主循环推进
        assert t > t_                            // 时间单调
        t_ = t;  caches_.InvalidateAll()         // INV-4 帧切换即失效

    func Context() -> FrameContext:
        return { t: t_, cache: caches_ }         // 换算/查询的唯一合法 t 来源
```

### [7] ConvertService — 换算服务（协调者）

**功能**：唯一允许跨组件协调的模块。LCA 行走、场景仲裁、近亲/远亲策略选择、热对合成矩阵缓存。**所有坐标换算的唯一入口**。

```pseudo
module ConvertService:
    registry_: &SceneRegistry
    tree_:     &AnchorTree
    pairCache_: map<(SceneId,SceneId), Transform>     // 热场景对合成矩阵

    func Point(from, to, p, fc) -> Vec3d:
        sa = registry_.OwnerOf(from); sb = registry_.OwnerOf(to)
        lca = PathCode.LcaDepth(from, to)
        if sa == sb or lca >= min(from.depth, to.depth) - 2:
            return Walk(from, to, p, fc)               // 近亲：LCA 行走 (P5)
        if t = pairCache_.Find({sa,sb}):               // 热对：一次矩阵乘
            return t * LocalToSceneRoot(sa, from, p, fc)
        pa = LocalToSceneRoot(sa, from, p, fc)         // 远亲：烘焙矩阵
        return registry_[sb].invRootTransform * (registry_[sa].rootTransform * pa)

    func Walk(from, to, p, fc) -> Vec3d:               // 核心行走 (算法 S3)
        cur = from
        for d = from.depth downto lca+1:               // 上行 子→父
            tr = tree_.TransformAt(cur, fc)
            p  = tr.rotation * p + tr.origin
            cur = PathCode.Parent(cur)
        for d = lca+1 to to.depth:                     // 下行 父→子
            tr = tree_.TransformAt(PathCode.Prefix(to, d), fc)
            p  = tr.rotation.Conjugate() * (p - tr.origin)
        return p

    func Velocity(from, to, p, v, fc) -> Vec3d:        // 与 Point 同链同 t
        // 上行每步: v ← R·v + ω×(R·p) + OriginVelAt(t)；下行取逆
```

## 四、Find 的跨组件编排（示例）

Find 不是独立组件，而是**调用方对各组件的编排**——这本身就是设计决策：组件提供原语，查询是原语的组合：

```pseudo
func Find(sceneName, center, radius, topN) -> [ObjRef]:       // 编排层
    fc  = FrameClock.Context()                                // [6]
    sc  = SceneRegistry.ByName(sceneName)                     // [1]
    assert sc.state >= Loaded                                 // 换算不需要加载，查询需要
    base  = PathCode.AnchorOf(sc.model, sc.rootPath, center, EpsFor(radius)) // [2]
    cells = sc.model.NeighborCells(Local(center, base), radius)              // [5]
    cand  = []
    for c in cells:
        path = base.ReplaceLastSegs(c)
        cand += ObjectStore.ScanBucket(path)                  // [4]，虚拟路径自动为空
    r2 = radius²
    hits = [o | o ∈ cand, sc.model.DistanceSq(o.pos, center) ≤ r2]  // [5] 度量
    return PartialSort(hits, topN, by DistanceSq)
```

## 五、模块化设计的三条边界纪律

1. **数据只有五种**——任何想传第六种数据的需求，先问是不是该进 FrameContext 或该成对打包（路径+坐标）；
2. **依赖单向**——下层不知道上层存在；CoordModel 被注入而非反向调用；ConvertService 是唯一的协调者，防止组件两两纠缠成网状依赖；
3. **写权限唯一**——只有 ObjectStore 写对象、只有 Registry 写场景、只有 AnchorTree 写节点表、只有 FrameClock 推进时间。**每个可变状态有且仅有一个所有者**，查询方全是只读——并发模型（读写锁、RCU、thread_local 缓存）由此自然成立。

这套分解的直接收益：七个组件可以独立实现、独立测试（对照说明书第 8 节的测试清单按组件分配），且 AI 编码代理可以按依赖序（PathCode → Kinematic/CoordModel → AnchorTree → ObjectStore → Registry → ConvertService → FrameClock 集成）逐个交付。
User: 会不会一个物体同时在多个空间树的节点里面
Kimi: **按设计：同一时刻，一个对象在树里有且仅有一个归属节点**——这是公理 A2（单归属）和不变式 INV-2（归属最深性）明文规定的。但这个问题值得掰开，因为"会不会同时出现"在三个层面有不同的答案：

## 1. 稳态下：严格唯一，而且这是刻意买来的

经典空间索引恰恰在这里吃过亏，两种传统方案都不干净：

- **重复存储**（如四叉树的 MX 变体）：对象跨界就拷进多个节点，空间换查询——代价是更新要改多处、查询要去重；
- **上提存储**（如标准八叉树）：跨界对象上提到能完整容纳它的祖先节点——代价是粗层级节点堆积大对象，查询每层都得扫。

本内核的选择是第三条路：**对象按其几何尺寸挂在"恰好容纳它的最深节点"**。一个大对象（比如横跨多个小 cell 的空间站）不去细粒度节点挤，而是挂在粗一级的节点——层级本身就是尺寸的表达。查询端配合的是**邻域展开**（NeighborCells 按半径把覆盖的 cell 都枚举到）加上**从粗到细的逐层桶扫描**，所以归属唯一也不会漏。

这套设计买来的东西：
- **Find 结果天然无重复**，不需要 seenItems 去重集合——你最初那段代码里的 `unordered_set<string> seenItems` 就是多级重复扫描的补丁，在这里被不变式从源头消灭；
- **Transfer 只动一处**，迁移成本 O（链长）；
- **对象状态只有一个真相源**，并发模型的"写权限唯一"才成立。

## 2. 迁移瞬间：短暂双桶可见，这是刻意允许的唯一例外

Transfer 的"先写新桶、后删旧桶"（INV-5）意味着在两步之间，对象**物理上同时出现在两个桶里**，持续一个窗口期。这不是事故，是原子性设计：

```
时刻1: 对象 ∈ 旧桶
时刻2: 对象 ∈ 旧桶 ∪ 新桶     ← 窗口期
时刻3: 对象 ∈ 新桶
```

但注意这个"同时"不会泄漏到查询结果里：**Find 走单一路径扫描，一次查询只会命中其中一个桶**。窗口期的语义是"任意并发读至少在一处看到对象"（不丢失），而不是"查询会返回两次"。所以逻辑归属在每一刻仍然唯一——双桶只是物理层的迁移中间态。

## 3. 概念上：一棵树上唯一，但"多棵树"是真需求——那不属于内核

如果你的问题指向的是"一个物体同时属于多个空间划分"——比如一颗卫星同时在"太阳系锚点树"里、又应该在"通信覆盖区树"和"行政空域树"里——这是**真实存在的多归属需求**，但本内核**故意不支持**，原因在前面讨论过：树结构的本质是单父层级，多视角正交划分没法塞进一棵树还不破坏其他不变式。

解法是在边界外做加法：

- **主树（几何内核）**：唯一归属，承担定位、精度、迁移、近邻；
- **辅助索引（外围模块）**：每种正交视角（电磁覆盖、行政区划、语义分组）各自维护一个 `ObjectId → 视图内位置` 的映射表或独立索引，查询时先查辅助索引拿到 ObjectId 集合，再回主树取坐标。

辅助索引只存"引用 + 视图内键"，不存坐标副本——**坐标永远只有主树一份**，避免了多归属系统最头疼的多副本一致性问题。对象迁移时，辅助索引靠事件订阅（Transfer 完成后发通知）惰性更新。

## 小结

| 场景 | 会同时在多节点吗 |
|---|---|
| 稳态存储 | 不会，INV-2 保证唯一最深归属 |
| Transfer 窗口期 | 物理上短暂双桶，逻辑归属仍唯一，查询不会重复返回 |
| 大对象跨 cell | 不拆不拷，挂在匹配其尺寸的粗节点 |
| 多视角空间划分 | 主树不支持，由外围辅助索引以"引用而非副本"的方式实现 |

一句话：**归属唯一是这个体系换取查询无去重、迁移低成本、并发可推理的根基，唯一被允许的"同时在两处"是迁移窗口期的物理中间态，而它经过设计保证对查询不可见。**
